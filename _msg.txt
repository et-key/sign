feat: `Char` を Layer 2 の型にした（表現が実行時の長さで変わらないように）

`.rodata` へ入る前に「動的型付けになっていないか」を確かめて、穴が見つかった。

  f : c ? c = \0
  a : f \5       ` 1文字
  b : f `ab`     ` 2文字

`f : String -> String` であり、**同じ関数が1文字と2文字の両方で呼ばれる**。だが
1文字は符号位置としてレジスタに乗り、2文字以上は `{ptr, len}` の参照である
（stack_abi.md §4.6）。つまり**表現が実行時の長さで変わる**——それは実行時に
見分ける必要があるということであり、動的型付けである。Sign が持たないと決めたものを、
気づかずに要求していた。

いまは2文字以上が診断で止まっているので顕在化していないが、`.rodata` を入れた瞬間に
誤ったコードが出る。

## 答えは潰れの規則にあった

`String ≅ List(Char)` であり、1要素のリストはスカラーと同型（`[5]` は `Int`）。
したがって**1文字の文字列は `Char` 1個そのもの**である。`String` は常に2文字以上に
なり（1文字は `Char` へ潰れ、0文字は `Unit`）、表現が型だけで決まる。

  Char    1文字（符号位置）    レジスタ（記憶上は charset 幅）
  String  2文字以上の並び      {ptr, len}

新しい概念ではない。`value_representation.md` §3 は以前から「Char 型の値域」
「Char の niche」と書いており、`type_system.md` も `0u` の NOTE で「`String`（Char）」と
併記していた——**概念はあったのに Layer 2 の型になっていなかった**。今日何度も見た
「語彙がモデルに追いついていない」形である。

## なぜ Char を作る方が安いか

`String` を常に `{ptr, len}` にする案（Char を作らない）もあった。だがそれだと
`is_digit : c ? \0 <= c <= \9` が中身の比較になる。仮引数の長さは静的に分からないので
1文字だと分かっていても縮められず、**字句解析の最内ループが常に間接参照**になる。

`Char` を分けると、追加のコストは「Char が String の位置へ流れる境界での持ち上げ」だけ
である——トークンごとであって、文字ごとではない。`take_while` のように「1文字以上」を
返す関数は `Char | String` になり、広い方に揃えて `Char` の枝を持ち上げることになる。

## 波及

余積の吸収則を `Char` へ広げた（文字を並べれば文字列である）。レンジの端点は `Char` に
なり（2文字以上は点ではない）、文字の範囲は `String` を返す。ブラケットの rest は要素が
`Char` なら器が `String` になる——`List(Char)` と `String` は同じものであり、別の名前を
持たない。Pass 4 はリテラルの形ではなく**型**で分岐するようにした。

  n_queens.sn    3 →  3
  lexer.sn       8 →  7
  parser.sn      6 →  6
  preprocess.sn 23 → 21
