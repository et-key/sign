Sign's space-application grammar was originally modeled on natural-language sentence structure (`list_model.md` §4.1: binary-operator right-hand-side is "the object of the verb"). This raised a real fork for `x f y` where `f` is a user-defined Lambda value (not a builtin operator like `+`):

- **Option A (rejected)**: treat `x f y` as true SVO infix — x and y bind *simultaneously* as f's 1st/2nd positional args (so `2 [+] 3` would literally equal `2 + 3`). Elegant symmetry with builtin operators, but needs a brand-new "Atom-Lambda-Atom triple" resolver rule, and doesn't generalize cleanly past arity 2.
- **Option B (chosen, 2026-08-05)**: `x f` (`apply_reverse`, coproduct_resolver.md §3 tier 10.3) is UFCS-style receiver-piping only — `x` is passed as a single argument to `f`, nothing more. Multi-arg "verb + object(s)" is written prefix (`f x y`) as normal. The user's stated reason: this matches an OOP-flavored calling convention already implied by the language, `f : [foo bar ~this] ? ...` (bracket-eager param destructuring where `~this` is the receiver/self by convention) — and it's important that struct destructuring and reverse-apply's receiver-passing use the *same* mechanism as plain reference-passing destructuring, not a special-cased one ("one way to express one thing", see [[feedback-implementation-style]]).

**Why this matters for future work:** Don't propose Option A (infix SVO calls for arbitrary Lambdas) — it was considered and explicitly rejected in this session. `apply_reverse` should stay a plain single-argument fallback.

**Implementation fallout (2026-08-05, `alpha/javascript`):** This surfaced a real bug: `pass2.js`'s tier-10 (coproduct/space) reduction was a single greedy leftmost-match scan that didn't respect `coproduct_resolver.md` §4's documented sub-priority order (10.5 compose → 10.4 apply → 10.3 apply_reverse → 10.2–10.0 concat/push/construct) — e.g. `5 inc 3` (inc:x?x+1) reduced `(5, inc)` via apply_reverse *before* `(inc, 3)` ever got a chance via apply, letting apply_reverse "steal" an atom that should've gone to normal forward application. Fixed by splitting tier 10 into four explicit exhaustive sub-passes (`COPRODUCT_PHASES` in `pass2.js`). `apply_reverse` evaluation itself was also entirely unimplemented in `interpreter.js` (threw `未対応の演算`) — added as `applyClosure(f, [x])`, reusing the exact same `bindParams`/completeness-axiom path as forward `apply`. Verified: `5 inc 3` → `[5, 4]` (apply wins, no stealing), `5 inc inc` → `7` (UFCS chain via compose-then-reverse-apply). See `alpha/javascript/README.md`'s `pass2.js`/`interpreter.js` entries for full detail.

**Further constraint confirmed same session (2026-08-05):** apply_reverse's left side must always pass exactly **one** argument to the Lambda — no multi-argument expansion, even via postfix `~` (which normally spreads a List into multiple positional args for forward `apply`, needed for the `sum : x ~xs ? x + (sum xs~)` recursion pattern). Implemented by having `apply_reverse`'s evaluation skip the shared `evalArgValues` expand-spread helper and always do `applyClosure(f, [evaluate(node.left, env)])` — one value, unconditionally. Verified: `pair : a b ? a` then `[1 2]~ pair` → `__` (the array `[1,2]` binds as `pair`'s single arg `a`, `b` stays Unit with no default → completeness axiom collapses the call), not `pair(1,2) = 1`.

**Pointfree implemented, and it needed one more apply_reverse rule (2026-08-05, same session):** `[+]`/`[+ 1]` (bare/pointfree operators) were later implemented — see [[project-sign-bracket-destructuring]] for the full story. Short version: a greedy multi-arg pointfree chain (`[+] 1 2 3 4 5`) needs to keep extending via `apply` past a single argument, but making `getCategory` say "always Lambda" for that globally broke apply_reverse again (`1 2 [+] 3 4` — after `[+]` finished consuming 3,4 into 7, it stayed "Lambda" forever and apply_reverse wrongly tried to feed `2` into the already-computed 7). The user's resolution, stated directly: **pointfree Lambdas are categorically excluded from apply_reverse, regardless of which operator** — pointfree only ever has one calling convention (forward prefix, `[+ 1] 5`), it doesn't also get the UFCS receiver form. This is now a general rule (`isPointfreeLambda` checked in the apply_reverse phase filter), not just a fix for `+`. Combined with confining the "keep extending" behavior to a Phase2-only bypass (so the chain naturally reverts to plain Atom once nothing's left to consume), `1 2 [+] 3 4` now correctly gives `[1, 2, 7]`.

**Still open, not yet fixed:** prefix/postfix hole-marker pointfree (`[!_]`, `[_!]`) and the trailing-comma map/select sugar (`[* 2,]`, `[< 3,]`) — see [[project-sign-bracket-destructuring]] for details.
