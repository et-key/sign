Surfaced 2026-08-08 while debugging a curried helper during the [[project-sign-8queens-audit]] work. Explicitly a "remember this for later" instruction, not a request to implement now — user's words: "未実装が多いから、まだここまでの話にたどり着けないんじゃないかと思ったので、内部的に覚えて置けるようにしておいて" (a lot is still unimplemented, we probably can't get this far yet, just keep it in mind internally).

## The design

**Manual/explicit curry form:** `f : x ? $[y ? ...]` — a curried function's outer lambda doesn't return the inner lambda *as a bare value*; it returns `$[...]`, the **address** of the inner lambda. Under Sign's `$`/`@` model (address-of / dereference, see `unit.md` §0.4), a curried continuation is represented as a function pointer, not an inlined closure value.

**Automatic currying = compile-time desugaring of that pattern.** Writing `$[...]` by hand at every curry step is tedious, so the language-level idea is: whenever the compiler detects an **arity shortfall** at an application site (statically known arity N, but only M<N arguments supplied), it should immediately synthesize the equivalent of the manual form — concretely, emit:
1. An **anonymous struct** holding the arguments already captured (the closure environment).
2. A **function pointer** to the continuation code expecting the remaining parameters (the pointed-to code can be assumed to live in a temporary stack save — no elaborate heap/lifetime story needed).

This is standard closure-conversion / partial-application-object technique (same shape as GHC's PAP objects or OCaml's closure representation: a partial application *is* {code pointer, captured environment} synthesized at the point arity isn't met) — expressed in Sign's own vocabulary because `$` already names "address of a function" as a first-class concept.

## Why this isn't the same as what got tried (and reverted) this session

During the queens work, hit `(f x) y` not apply-chaining and tried a narrow static fix in pass1.js/pass2.js (`curriedBody` flag: does a lambda's body itself look like another `<params> ? <body>` lambda-definition, propagate "still Lambda" one level past declared arity). That was reverted (`git checkout -- pass1.js pass2.js`) once the user redirected to the real underlying problem (mixed bracket-destructured params, see [[project-sign-8queens-audit]]).

The user's `$[...]`-based design is a different and more general fix: instead of a special-cased static AST-shape check for "does the body look like a lambda," it's "any undersaturated application produces a closure, unconditionally, as a general runtime/compile-time rule" — no need to inspect the body's shape at all. That's the correct general mechanism; the `curriedBody` hack was a narrow band-aid for one shape of the same underlying gap.

## Why not implementable yet

- `alpha/javascript` is a tree-walking interpreter with no real "compile time" codegen phase — the closest analogue would be pass2's static apply-vs-construct arity check (`getCategory`'s `depth < binding.arity`), which already exists for *known-arity* identifiers but doesn't currently synthesize a reusable closure for the undersaturated case.
- `$`/`@` (address-of / dereference) are **not implemented** in `interpreter.js` at all — `evalUnaryOp` throws `未対応の前置/後置演算` for anything other than identifiers, calling it explicitly "アドレス操作のため未対応" (see the currying-avoidance discovery this session: `@(f 10)` threw immediately). Since the manual form is defined *in terms of* `$`, there's no way to even express — let alone auto-desugar to — the target form until address-of exists as a real value the interpreter can produce and re-apply.

## Correction (same session, later): the fix must be compile-time, not a runtime fallback

My first "how to apply" draft (below, now superseded) suggested making `applyClosure` dynamically return a partial-application closure whenever `argValues.length < arity` — i.e., a **runtime** check inside the interpreter's apply path. The user corrected this directly: Sign has an already-settled, standing design assertion ("断定") that **the compiler must never leave anything for the runtime to decide** — nothing resembling type inference, dispatch resolution, or "figure out what to do" logic may run *during* program execution; all of that has to be fully resolved by the time compilation finishes. This isn't new — it's the same principle Pass1b's generic dispatch already embodies (`@ref` specialization is done by statically enumerating every call site at compile time; `compiler_pipeline.md` §6.3 makes an export with zero call sites a **compile error**, precisely so the compiler is never in a position of "I don't know who might call this, so I'll have to check at runtime").

Important nuance the user added when I initially over-corrected into "so *no* runtime indirection is allowed at all": that's too strict, and even C doesn't satisfy it in that sense. Calling through a function pointer stored in a struct (e.g. `qsort`'s comparator callback) is, operationally, indistinguishable at the CPU level from a dynamic language's virtual dispatch — a value is loaded and jumped to. That's *fine* and doesn't violate the static principle, **as long as the compiler already fully decided, ahead of time, the struct's shape and the complete set of possible jump targets** — nothing is left for the *compiler itself* to figure out mid-execution. So: runtime jumps through precomputed pointers = OK. Runtime *decisions about what to allocate, how long something lives, or what code even exists* = not OK. The auto-curry mechanism has to land on the "OK" side of that line: the struct shape and the continuation address are both compile-time-determined; only the *jump* happens at runtime, same as any compiled function call.

## Why this rules out malloc/free, and what doesn't: named (`:`) and exported (`#`/`##`/`###`)

Extending the same principle to the storage/lifetime question ("僕の中では答えは自明。`:`で名前を付けたか？前置`#`系でエクスポートされてるか？がカギ" — the answer is self-evident to me: whether it was named with `:`, and whether it's exported via the `#`-series prefix, are the key facts): a generic heap allocator (`malloc`/`free`) is disqualified for the same reason a runtime-dispatch fallback is — deciding *when* to free something requires either a GC scan, refcounting, or a programmer call sited at a point whose reachability can vary with runtime data flow. All three are the compiler (or the running program standing in for it) making a lifetime decision *during execution*, which is exactly the thing ruled out above.

The naming/export system Sign already has turns out to already supply everything needed to avoid this, with no new mechanism required:

- **Unnamed** (no `:` — e.g. the anonymous struct an auto-curry step synthesizes): nothing in the program has any way to refer to it beyond the expression that produced it. Its lifetime is trivially the enclosing call frame — stack-scoped, freed automatically by the call/return protocol, no `free()` needed at all.
- **Named but not exported**: referenceable only within its own lexical scope and nested scopes, which are fully visible in the source. The compiler can enumerate every possible reference by just reading the scope — still fully closed, still no runtime lifetime question.
- **Named and exported (`#`/`##`/`###`)**: this is the case that looks like it "escapes" into an open, unknowable world — except `compiler_pipeline.md` §6.3's existing rule ("an export with no call site is a compile error") guarantees this can never actually happen. An exported symbol's set of references is still finite and fully enumerable — that's not a coincidence, it's Pass1b's whole callsite-enumeration mechanism (already implemented, see [[project-sign-status]]/[[project-sign-8queens-audit]]'s pass1b tests) doing double duty as a closed-world guarantee for lifetime analysis, not just for generic specialization.

So in every case — unnamed, named-private, or named-exported — the compiler has, by construction, complete static knowledge of every place a value could ever be referenced from. There's structurally no scenario where "we don't know when this dies, so we need a runtime allocator to find out" can arise. **This is why the type system is a prerequisite for `$`/`@`**, not a parallel or optional feature: the type system is what would let the compiler actually *use* this closed reference-set information to prove a scope/lifetime and pick a static allocation strategy (stack, or some other compile-time-sized region) instead of ever reaching for a general-purpose heap.

**How to apply:** the corrected version of "how to apply" from the original entry: don't make `applyClosure` dynamically synthesize partial-application closures at runtime. The struct shape and continuation address for an undersaturated call need to be decided the same way Pass1b already decides generic specialization — by statically walking call sites — before execution starts. And when actually building `$`/`@`'s storage model, the `:`/`#` naming-and-export facts already on every binding are the thing to key allocation-strategy decisions off of, not a new lifetime-tracking mechanism bolted on separately.

## Resolving the apparent type-system ↔ $/@ circularity: it's layered, not circular

User flagged this directly: "型システムと `[$_]` `[@_]` `[#]` は、現状だと互いが互いを参照する情報のままになっているように感じている" (the type system and $/@/# still feel like they're stuck referencing each other). Worked through it and the user confirmed the resolution: **it isn't actually a cycle, it's three separable information layers that got flattened into one word ("type system") — and this problem can only be solved by climbing that layered ladder one rung at a time ("そういう段階的な解決の階段でしかこの問題は解決できない"), not by picking one side to build first as if the other didn't matter.**

1. **Scope/naming/export (already exists, Pass1 — `pass1.js`'s `buildEnvScope`).** Whether a binding is named (`:`) and whether it's exported (`#`/`##`/`###`) is pure syntactic/structural information, available *today*, with zero dependency on type inference. This is exactly the lifetime-determining information from the section above — it's independently sufficient to decide *when* something can be freed, without needing to know *what* it is.
2. **Shape/layout (not yet built, a new lightweight pass — distinct from both Pass1 and Pass3's type inference).** `$x` needs to know how many fields/bytes `x` occupies to actually allocate/interpret memory, and `@` needs the same to read it back correctly. This is *not* the same job as Pass3's type inference (unification, generic instantiation, Struct-vs-Dict-vs-Scalar classification) — it's a much shallower "what shape does this expression have" query that could plausibly be answered by walking the AST structurally, the same spirit as Pass1a's `atomType` (reads types straight off literals, no inference) rather than Pass3's heavier machinery. This layer doesn't exist yet as a separate thing — it's currently entangled with Pass3 in people's heads (mine included, until this conversation) but doesn't actually need to be.
3. **Layer-2 type classification (Pass3, `pass3.js` — Address/Float/String/Vector/List/Struct/Dict/Unit).** This is where "Address" gets its full meaning as a type category others can reason about, trait-check, etc. (see [[project-sign-type-philosophy]]). This layer can only be *fully* meaningful once layer 2 (shape/layout) exists to back it with something concrete — but layer 2 doesn't need layer 3 to exist first.

The dependency graph is 1 → 2 → 3, a strict order, not 1↔3 or 2↔3 feeding back on each other. The circularity was an illusion caused by treating "type system" as one undifferentiated thing instead of noticing that layer 1 already exists and doesn't need the others, and layer 2 (the actually-missing piece) is smaller and shallower than it first looks — closer to Pass1a's already-implemented literal-reading `atomType` than to Pass3's inference engine.

**How to apply:** if `$`/`@` implementation ever gets picked up for real, the build order suggested by this is: (a) lean on Pass1's existing naming/export data for lifetime — nothing new needed there — then (b) build the shape/layout pass as its own thing, don't try to bolt it onto Pass3 or wait for Pass3 to grow into it, then (c) only after both exist does it make sense to flesh out "Address" as a proper Layer-2 type category others can build on.

## Update (same day, commit 1651c84): the manual form is now real — but only the manual form

Right after this whole design conversation, the user said "とりあえず実装しよう" and `$`/`@`/`#` got a first implementation in `interpreter.js` (see [[project-sign-8queens-audit]] for full detail — this file stayed as design-only, that one has the concrete commit). What's actually built:

- `$x` (identifier operand): a real read/write reference into the variable's binding (walks the env chain to find which scope owns `x`, returns `{get, set}` closing over that scope's Map).
- `$[list ' idx]` (get_prop operand): same idea for a list element.
- `$[expr]` (anything else, including a fresh lambda literal — the curry case): a **read-only snapshot** reference. No write-back, because a value that was just computed and isn't stored anywhere has nowhere to write back *to* — this is fine because the curry idiom only ever needs to read/call through it, never mutate it.
- `@`: unwraps a reference (`.get()`); passes any plain (non-`$`-produced) value through unchanged, so `@f 1` behaves the same whether `f` holds a bare Lambda or something `$`-boxed.
- `#`: writes the right operand through a left-hand address reference (`.set()`).

**Confirmed working end to end:** `f : a ? $[b ? a + b]` called as `@(f 1) 2` → `3` — the exact manual curry calling convention from this whole design thread, now actually executable. Also confirmed real write-through: `$[array ' 0] # 99` then reading `array` shows the mutation.

**Still NOT done, and deliberately not attempted in that commit:** automatic currying (the compile-time struct+function-pointer synthesis on arity shortfall, described above). This implementation only makes the *manual* `$[...]` idiom usable — a curried function still has to be hand-written with explicit `$[...]`/`@(...)`, nothing auto-desugars yet. The "must be compile-time, not a runtime `applyClosure` fallback" constraint from above still fully applies to that remaining piece. Also not done: the shape/layout pass (layer 2 from the section above) — the current `$`/`@` implementation sidesteps needing it by only supporting identifier/get_prop/snapshot references (all cases where JS's own value representation already tells you enough to read/write correctly), not general Struct field-level addressing.

## Automatic currying landed too, same day (commit 10f0777) — the design closed out exactly as specified

Right after the `$`/`@`/`#` commit, the user said "自動カリー化をやろう！" and it got built, honoring every constraint worked out above:

- **Static, not runtime.** `pass2.js` gained `markUndersaturatedApplies`, which walks the *fully-reduced* AST after `reduceAll` finishes and renames any apply-chain that's short of its callee's arity to `"partial_apply"`. `interpreter.js`'s evaluator has a dedicated case for that node type that unconditionally builds a partial closure — there is no runtime check anywhere of the shape "if not enough args, then...". The decision was already made by the time execution starts, exactly the "C function-pointer jump, not a dynamic-dispatch decision" line from the correction above.
- **Paren-crossing arity tracking, the way `(f x) y`-style curry chains actually get written.** A new `resolveKnownArity` helper lets both `getCategory` (deciding whether to keep extending a chain within one expression) and `markUndersaturatedApplies` (deciding whether to curry) see *through* a one-line paren block to the arity of what's inside — so `(f 1) 2 3` and `((f 1) 2) 3` both resolve correctly, not just the single-paren-crossing case.
- **The "must not overreach" edge this design implied but hadn't been tested against:** default-having params must NOT trigger currying (`g 3` where `g`'s 2nd param defaults should still just use the default, not become a permanent partial closure), and rest params must NEVER curry (they're variadic, "short by N" isn't a meaningful question for them). Both needed pass1.js to grow a `requiredArity` (excludes defaults and rest) *separate from* the existing `arity` (total slot count, still used unchanged for "keep extending within one expression" — rest params still correctly report `Infinity` there). Two real regressions surfaced and got fixed working through this (an infinite-recursion bug from a chain-collector name mismatch, and the default-arg regression) before all 133 tests passed again.

**Confirmed end to end:** `f 1` for a 3-arg `f` → a real callable partial closure; `(f 1) 2 3` and `((f 1) 2) 3` → both complete correctly; fully-saturated calls, explicit-Unit completeness-axiom collapse, and rest-param behavior are all byte-for-byte unchanged; the full [[project-sign-8queens-audit]] 8-Queens program still solves N=1..8 correctly; the manual `$[...]`/`@(...)` form from the previous commit still works unchanged alongside this.

**What's left from this whole design thread:** only the shape/layout pass (layer 2) — needed for addressing into arbitrary Struct fields, not needed for what's built so far since currying/manual-$/@ only ever needed identifier/list-index/snapshot references, all of which JS's own representation already covers.
