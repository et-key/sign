After the guide-example audit ([[project-sign-bracket-destructuring]]) wound down, the user asked to verify operator precedence correctness before moving into type-system work (`type_system.md` §4's per-operator type-signature table). This surfaced two different kinds of finding.

## Fixed: List-List-no-tilde silently collapsed to Unit

`[1 2 3] [1 2 3]` (two List blocks placed via space, neither with postfix `~`) evaluated to `__` instead of becoming a 2D array. Root cause: `coproduct_resolver.md` §5.2-2 says this case ("~なしのList同士の並置") should be "kept as an independent Atom (a list of 2 references)" — but `pass2.js`'s `coproductReduce` implemented "kept" as literally returning `null` (leave the pair unreduced). When these two blocks are the *entire* line, that leaves `items.length !== 1` after all reduction tiers, so `reduceAll` falls to `{type:"unresolved"}`, which `interpreter.js`'s `evaluate()` silently turns into `UNIT` (no case matches it, falls through to the default return). Fixed by returning `mk("product", a, b)` instead of `null` — `list_model.md` §2.2 explicitly states the equivalence `[1 2] [3 4] = 1 2 , 3 4`, and the `product` node (fixed earlier this session, see [[project-sign-bracket-destructuring]]) already wraps non-chained operands as `[l, r]` peers, giving exactly the right 2D-array shape. Verified `[1 2] [3 4]` and `1 2 , 3 4` now produce byte-identical output; concat (`[1 2]~ [3 4]~`) and `sum_list` unaffected. User found this by direct inspection ("[1 2 3] [1 2 3] が __ に落ちるけど、2次元配列にならないとね"), not from a systematic audit pass.

## Found, not (yet) acted on: the two canonical spec files disagree with each other

`alpha/javascript/operator_table.js` is byte-for-byte identical (modulo comments) to `documents/ja-jp/impl/syntax/operator_table.js` — so alpha/javascript faithfully implements that file. But that `.js` file and the prose table `documents/ja-jp/impl/syntax/operator_table.md` — both nominally "canonical" — disagree:

- Postfix `@` (import): `.js` places it at precedence 22 (alongside postfix `!`/`~`), `.md`'s table row says precedence 24.
- Prefix `-` (negate) and `><` (reverse) exist in `.js` at precedence 23 (with `-` carrying a code comment admitting "仕様書に明記は無いが事実上の前置演算子" — not in the spec, but a de facto prefix operator) — **neither appears anywhere in `.md`'s exhaustive operator table.**
- Several `.name` disambiguations in `.js` (e.g. `!==`→`not_equal` colliding with `!=`'s `not_equal`, rather than `.md`'s distinct `xnot_equal`; `=`→`assign_equal` vs `.md`'s `equal` which would collide with `==`'s `equal`; `'`/`@` at tier17 → `get_prop`/`get_at` vs `.md`'s `get`/`get`) look like deliberate collision-avoidance in the `.js`, not really bugs — `.md`'s "機能" column reads more like a loose category label than a literal identifier spec.

**Resolved (follow-up session, 2026-08-06):** went through all three `.js`-vs-`.md` naming discrepancies with the user's framework "if it affects implementation, fix it directly; if it's just a documentation-wording matter, no action needed." Verdict: only `!==` vs `!=` was a *real* problem — both literally shared `.name: 'not_equal'` **within `operator_table.js` itself** (not just a `.js`-vs-`.md` mismatch), which is why downstream code (`pass3.js`, `interpreter.js`) had to fall back on checking `.op` instead of `.name` to tell them apart — a genuine internal collision, not just loose prose. Fixed by renaming tier-8 `!==` to `xnot_equal` in both `operator_table.js` files (documents/ja-jp canonical + alpha/javascript copy), matching what `.md` already called it — this closes the internal collision *and* the `.js`-vs-`.md` mismatch in one move. Verified zero behavioral change (existing `.op`-based checks in `pass3.js`/`interpreter.js` don't care about `!==`'s specific name value, they check `.op==="!="` explicitly to admit only `!=`), only the error message for `1 !== 2` changed (`未対応の演算 'not_equal'` → `'xnot_equal'`, more accurate/distinguishable). The other two pairs (`=`/`assign_equal` vs `.md`'s "equal"; `'`+`@`/`get_prop`+`get_at` vs `.md`'s "get"/"get") were confirmed **not** real collisions — `.js` already uses distinct names for each, the `.md`'s "機能" column just reuses common descriptive words across unrelated rows (natural-language column, not a machine-checked identifier) — left as-is, no fix needed.

**Also added while here:** the previously-discussed-but-never-written `-`(negate) row was finally added to both `documents/ja-jp/impl/syntax/operator_table.md` and `documents/ja-jp/guide/operator_table.md` (near-duplicate files kept in sync) — tier 23, Unit-operand behavior 吸収元 matching `interpreter.js`'s `evalUnaryOp`.

This is **not an alpha/javascript implementation bug** — it's an inconsistency between two files that both claim to be the authoritative spec. Needs the user's judgment call on which to trust / whether to reconcile `.md` to match `.js` (the `.js` is what code actually consumes, so it's the practically-authoritative one, but `.md` is the human-readable "spec of record" per the project's own conventions). Not resolved — surfaced and left for the user to decide.

## Found via testing, confirmed real gaps (not yet fixed)

- **Range family**: `interpreter.js`'s range evaluation (added earlier this session, see [[project-sign-bracket-destructuring]]) only handles the `range`/`range_arithmetic` op names (plain `~` and `~+`). The other four documented derived range operators — `~-`/`range_arithmetic_rev`, `~*`/`range_geometric`, `~/`/`range_geometric_rev`, `~^`/`range_power` — all throw `未対応の演算` (confirmed via a probe: `[10 ~- 2 ~ 2]`, `[2 ~* 2 ~ 16]`, `[16 ~/ 2 ~ 2]`, `[2 ~^ 2 ~ 16]` all error). Straightforward to fix — same `buildRange`/`rangeStepFn` machinery already handles the step function dispatch by `op`, just needs the other 4 evaluate-switch cases wired up the same way as `range`/`range_arithmetic` were.
- **`><` (prefix reverse) still doesn't work**: confirmed again — `><[1 2 3]~` still silently evaluates to `__` rather than reversing. This was already noted during the earlier list_cheat_sheet audit ([[project-sign-bracket-destructuring]]) as a lexer-marking issue (the density-attachment marking in `lexer.js`'s `separateInfix` doesn't seem to recognize `><` as a prefix operator needing marking) — root cause not yet actually diagnosed, just reconfirmed still broken.

## Resolved same session: postfix `@` (import) precedence reconciled, and `><` (reverse) dropped entirely in favor of a better idea

Confirmed empirically that `resolveDensity` (prefix/postfix handling) never consults the numeric `.precedence` value at all — `lookup()` only filters by `position` (prefix/postfix/infix), and prefix/postfix combination order is purely positional/textual (postfix always wraps the core before prefix does, hardcoded, not precedence-driven). So the `.js` vs `.md` precedence-*number* disagreements are cosmetic for prefix/postfix ops specifically (don't affect current parsing) — but still worth reconciling for spec accuracy. Verified via probe: `@\`add.sn\`@` → `input(import(...))`, i.e. import always resolves before input regardless of the declared tier numbers, confirming the user's intuition ("import should happen before input") is already structurally guaranteed.

Given "higher tier number = binds first/tighter" and that import-before-input maps to import needing the *higher* number, `.md`'s placement (postfix `@`=24, prefix `@`=23) is the internally-consistent one; `.js`'s (postfix `@` folded into tier 22, below input's 23) was the one that needed fixing. **Fixed**: gave postfix `@`(import) its own dedicated tier 24 in both `documents/ja-jp/impl/syntax/operator_table.js` and `alpha/javascript/operator_table.js`, shifting blocks/indent/escape up by one (24→25, 25→26, 26→27). Also confirmed prefix `-` (negate, tier 23) is correctly positioned above `^`/pow (tier 15) per "sign inversion is arithmetic, follows algebraic precedence" — no code change needed there. **Doc row added (2026-08-06, follow-up session):** both `documents/ja-jp/impl/syntax/operator_table.md` and `documents/ja-jp/guide/operator_table.md` (near-duplicate files, kept in sync) now have the `23 | \`-\` | 前置※ | negate | ...` row, matching `interpreter.js`'s `evalUnaryOp` behavior (Unit operand → absorbs to `__`).

**`><` (reverse) — dropped as a planned addition, not just left broken.** Mid-discussion the user recalled that `<>` (mirror of `><`) was a well-established "not equal" symbol in old BASIC/Pascal/SQL — a real, meaningful design objection (conflicts with "symbol's natural meaning should match its operation," and Sign already has `!=` for not-equal, so `><` isn't even needed for that). Rather than bikeshed a replacement symbol (the only fully free ASCII symbol left is `.`), the user reframed the actual need: **the real requirement wasn't "reverse the whole list," it was "traverse/fold a list from the tail without materializing a reversed copy."** That's solvable by generalizing existing destructuring rather than adding a new operator.

**New feature, spec'd and implemented same session: rest-marker position generalization (`list_model.md` §2.5, new subsection).** `~name` in a bracket param list can now appear at *any* position, not just last. Non-rest entries before `~name` bind from the front (as before); non-rest entries after `~name` bind from the **back**, in written order; `~name` itself captures whatever's left in the middle. So `[x ~xs]` = traditional head/rest, `[~head tail]` = pop-from-the-end (`tail`=last element, `head`=everything else), `[first ~mid last]` = both ends at once — same mechanism as Python's `a, *b, c = list` extended unpacking. Implemented in `interpreter.js`'s `bindBracketParams` (List branch only — Dict destructuring is by key name, position doesn't apply there): split `entries` at the rest index into `before`/`after`, bind `before` positionally from the front, then compute `restEnd = max(idx, value.length - after.length)` so `after` entries claim the last `after.length` slots and rest gets everything strictly between. Verified with a `sum_rev : [~head tail] ? head & (sum_rev head) + tail | tail` recursive tail-fold (→ 15 for `[1 2 3 4 5]`) — concrete proof list-reversal-as-a-primitive is unnecessary once this exists. The `><` operator itself is now moot — it should probably be removed from `operator_table.js`/`.md` entirely rather than fixed, though that removal hasn't happened yet (not explicitly asked for).

**`><` actually removed, not just deprioritized (same session, 2026-08-06).** User's call: "リスト反転を消そう！" — deleted the `'><': {position:'prefix', name:'reverse'}` entry from both `documents/ja-jp/impl/syntax/operator_table.js` and `alpha/javascript/operator_table.js` (tier 23), replaced the `list_cheat_sheet.md` "リストの反転" row with a note pointing at §2.5's tail-destructuring and `reference.md`'s pre-existing `reverse : x ~y ? reverse y~, x` recursive-function example (which already demonstrated "no built-in needed" independent of this session's work — good corroboration found while cleaning up). No interpreter.js code needed touching since `reverse` never had an eval case to begin with (it silently fell through to `__` before removal, same after). Zero regressions (77/77).

**New finding while verifying the removal (unrelated, not yet fixed): `!=` (not_equal, tier 12) can't actually be evaluated at all.** `1 != 2` throws `未対応の演算 'not_equal'`. Root cause: `interpreter.js`'s dispatch to `evalCompare` is gated by `if (COMPARE_OPS[node.name])`, and `COMPARE_OPS` (`{less, less_equal, assign_equal, more_equal, more}`) does not include `not_equal` as a key — so `!=` nodes never reach `evalCompare` at all, meaning `evalCompare`'s own `if (op === "!=") {...}` special-case branch (the §4 exception logic, "x != __ = x" etc.) is unreachable dead code. Almost certainly `not_equal` was left out of `COMPARE_OPS` deliberately to avoid it colliding with tier-8 `!==`'s identically-named `not_equal` (see [[project-sign-bracket-destructuring]]'s note on `.op`-based disambiguation elsewhere in the codebase), but that omission also blocks the tier-12 `!=` that's supposed to use it. Found by accident while spot-checking that removing `><` didn't regress anything else — not investigated further, not fixed.

## `!=` evaluation bug fixed too (same session) — surgically, not the whole `==`/`===`/`!==` family

Investigating revealed `==`/`===`/`!==`/`!=` were **all** unevaluable — `test/pass2.test.js`'s "x == y" test only checks AST construction (it doesn't import `interpreter.js` at all), which had been silently passing as false reassurance that comparison operators "worked." Root cause for `!=` specifically: `evaluate()`'s dispatch to `evalCompare` is gated by `if (COMPARE_OPS[node.name])`, and `!=`'s `.name` is `"not_equal"` — deliberately absent from `COMPARE_OPS` because tier-8 `!==` shares that exact same `.name` (the established disambiguation convention in this codebase is to check `.op`, not `.name`, for this pair — see `test/pass3_param_usage.test.js`). So `!=` never reached `evalCompare` at all, even though `evalCompare` already had a correct, complete `if (op === "!=") {...}` branch (§4's exception rule: `x != __ = x`, `__ != x = __`) sitting there unreachable. Fixed with a single surgical OR-condition: `if (COMPARE_OPS[node.name] || node.op === "!=") return evalCompare(...)` — lets exactly `!=` through without touching anything else.

**Deliberately did not fix `==`/`===`/`!==` in the same pass** — user asked specifically to fix "the bug" (singular, referring to `!=`), and `!==` in particular raises an unresolved design question (`===`/"same" per `operator_table.md` means *identity*, not structural equality — but this interpreter has no address/binding-identity model at all, `$`/`@`/`#` being entirely unimplemented per [[project-sign-status]], so "what does `===` even mean here" isn't a quick fix). `!==` still throws `未対応の演算` (unchanged, honest) rather than being routed through a same-name-collision workaround that would silently apply the wrong Unit-propagation rules (`!==`'s documented rule is left/right-Unit → passthrough on both sides, genuinely different from `!=`'s left-absorbs/right-passthrough — they can't share one code path). If `==`/`===`/`!==` come up again, this is a bigger, separate task — not a copy-paste of the `!=` fix.

**Range-family gap fixed (2026-08-08, commit 187a970, see [[project-sign-8queens-audit]]):** turned out `rangeStepFn` already dispatched all 5 ops correctly — the actual bug was the 3-term `"range"` eval case's guard only matching the literal AST node name `"range_arithmetic"` (what `~+` specifically gets), while the other 4 operators get distinct names (`range_arithmetic_rev`/`range_geometric`/`range_geometric_rev`/`range_power`) that never matched, so `[10 ~- 2 ~ 2]` and friends fell through to evaluating the bare inner node and hit "未対応の演算" instead of building a range. Fixed by widening the guard to a `RANGE_ARITHMETIC_NAMES` set. All 5 confirmed working for the 3-term (bounded) form; the 2-term (no end, genuinely infinite Pull stream) form is still an intentional, clear error for all 5 — that part was correct and untouched.

**`==` implemented (2026-08-08, commit 94610e4, see [[project-sign-tco]] for what else landed same day):** turned out to be the easy third of the family, per the user's framing — "コンストラクタを持たない型付けのバイナリ同値性" (a typed binary equivalence with no constructor involved). `type_system.md` §6.2 spells this out explicitly: "`==` は常に純粋な構造比較（Hom集合の一致）であり、コンストラクタ名を一切参照しない" — recursive shape+value comparison (Scalar/String by value, List by length+elementwise, Struct/Dict by matching key sets + recursive per-key equality), confirmed against the doc's own `Point`/`Vector2D` example (same fields → equal, regardless of which constructor function produced them). Unit-isomorphic values (`__`/`[]`/`""`) compare equal to each other. Wired in the same surgical way `!=` was (`node.op === "=="` added to the `evalCompare` dispatch guard, `name="equal"` still absent from `COMPARE_OPS`).

**`!==` implemented too (2026-08-08, commit 346851f):** user's framing — "!== は今実装したものの否定" (!== is the negation of what was just implemented, i.e. of `==`). *Not* the same Unit rule as `!=` though — checked `operator_table.md` row 56 first rather than assuming: `!=` is asymmetric (left-Unit absorbs to `__`, right-Unit passes through the left value), but `!==` is symmetric passthrough on *both* sides (left-Unit → return right value, right-Unit → return left value; both-Unit → `__`, since that's structurally equal). `xnot_equal(l,r) = isUnit(l)&&isUnit(r) ? UNIT : isUnit(l) ? r : isUnit(r) ? l : (structuralEqual(l,r) ? UNIT : l)`. Verified the `!=`-vs-`!==` divergence is real and now directly observable since empty lists are Unit-isomorphic (commit 0902dc2): `[] != [1 2 3]` absorbs to `__`, but `[] !== [1 2 3]` passes through to `[1 2 3]` — same operands, genuinely different documented rules, not a bug in either. Also broadly re-verified `==`/`!==` against nested lists, lists of structs, and order-sensitivity (`[1 2 3] == [3 2 1] → __`, confirms lists compare as ordered sequences not sets) at the user's request ("せっかくだから、リストでのバージョンのテストもしておこう").

**Still open:** `===` ("same"/identity). Confirmed via `type_system.md` §6.2's own worked example that `===` is *not* simple address/reference equality (which `$`/`@`, now implemented — see [[project-sign-currying-design]] — would have been enough for) — it needs **constructor-provenance tracking**: `p === v` for two structurally-identical values from *different* constructor functions is `__`, resolved via `' !__` which Pass1 traces statically back to a named constructor binding when possible (`$Constructor`-style address), falling back to `__` when it can't (e.g. runtime-dispatched values). That's a materially bigger, separate feature — a Pass1-level provenance-tagging mechanism, not just a comparison function — not a copy-paste of the `==`/`!==` fixes.

**How to apply:** don't propose re-adding a "reverse" operator for lists — the design conclusion this session was that tail-position destructuring (§2.5) covers the real use case better, and `><` specifically is disfavored due to the BASIC/Pascal/SQL not-equal association. If asked "what happened to list reverse," point here.
