## Fixed & committed (bb63752): empty string as Unit, and string indexing as characters

Two straightforward extensions of principles already established earlier the same day:
- `string_and_comment.md` §1: empty string is isomorphic to `__` (parallel to the already-fixed `isUnit([]) → true`, see [[project-sign-8queens-audit]]) — `isUnit` now also returns true for `v === ""`.
- §6: a string is a sequence of characters, indexable the same way a list is (`` `hello` ' 0 `` should give `` `h` ``, confirmed against the doc's own example). `get_prop` previously wrapped a bare string as a 1-element array (same normalization used for scalars) instead of splitting it into characters — fixed by special-casing `typeof l === "string"` to `l.split("")`, and rejoining get-rest/multi-index results back into a string (not left as a character array) to mirror how the equivalent List operations already behave.

**User's framing, worth remembering:** when I reported these findings, the user pushed to view them through the SAME lens rather than as three unrelated new features — "この言語には評価の単位元が存在するから...最終行だけは確実に返値になる" and "その原理に従えば3つとも自明のはず" — i.e., don't invent new special-cases per type; recognize that a principle already nailed down for one domain (Unit as identity element, Scalar≅1-List) usually just needs to be *extended* to a second domain (String), not reinvented.

## Fixed & committed (4bca4cf): comments and code can coexist in one file, plus a real PEG-backtracking bug found while fixing it

`Program`'s grammar rule was `(SOL @Line EOL*)* / comment* EOF` — a **whole-file** either/or: either every line parses as code, or every line parses as a comment. A single comment line anywhere in a real (code-containing) program was an immediate parse error, since it doesn't fit the all-code branch and the file as a whole doesn't fit the all-comment branch either. The `comment` rule itself was correctly defined and even already returned `null`, but was structurally almost unreachable for any real file. Fixed by choosing `comment / Line` per line and filtering the resulting `null`s — same "Unit gets filtered out of construction" pattern `asList` already uses elsewhere.

Fixing that surfaced a **second, previously-invisible bug inside `comment` itself**: `comment = SOL "`" [^\r\n]* (EOL / EOF)` doesn't actually implement `string_and_comment.md` §2's stated lookahead rule ("closing backtick on the same line → string, not comment"). PEG's `*` repetition doesn't backtrack — once `[^\r\n]*` greedily consumes to end-of-line, if a later requirement fails, the whole containing expression fails outright, it does *not* retry with a shorter match. So a naive `!([^\r\n]* "`")` negative-lookahead attempt still failed, because `[^\r\n]*` inside the lookahead itself swallowed the entire rest of the line (including the closing backtick), leaving nothing for the trailing `` "`"` `` to match — the lookahead always "succeeded" (found no closer) even when one was right there. Confirmed concretely: `` `123` 123 `` (a real string-literal expression, has a closer) was being silently eaten whole as a comment. Fixed by excluding the backtick itself from the scanned character class (`!([^\r\n\`]* "`")`) — this makes the scan stop exactly where a real closer is, rather than running past it. **General lesson, worth remembering for any future PEG grammar work in this codebase: PEG repetition (`*`/`+`) is possessive, not backtracking — a lookahead pattern that needs to "find X somewhere before Y" must exclude Y's own trigger character from what it scans over, it can't rely on backtracking to retry shorter matches.**

Applied to both `alpha/javascript/sign.pegjs` (implementation) and `documents/ja-jp/impl/syntax/grammar.pegjs` (canonical spec copy) — confirmed byte-identical after, same sync convention `operator_table.js` already established (see [[project-sign-operator-table-audit]]). `en-us/impl/syntax/grammar.pegjs` deliberately left alone — it was already a stale, partially-diverged translation before this session touched anything (missing an unrelated `&"\x02"` alternative ja-jp already had), and keeping English docs in lockstep hasn't been this session's practice.

## Confirmed correct, not a bug (verified, no fix needed)

- Multi-line strings via `` ` `` + backslash + real newline continuation (§5, `text : \`Line 1\` \ \n \`Line 2\`` → `"Line 1\nLine 2"`) — works exactly as documented. First test attempt showed it broken, but that was my own JS-string-escaping mistake in the probe script (`\\n` instead of an actual embedded newline), not an interpreter bug — worth remembering to double-check probe scripts carefully before reporting a "found bug" when backslash/newline sequences are involved across multiple escaping layers (bash heredoc → JS string → Sign source).
- A function body's final line being a bare string literal correctly becomes that function's return value, in every shape tested (single-line body, indent-body sole line, indent-body last-of-several, string built via concatenation on the final line).
- Inline (trailing, same-line-as-code) comments genuinely don't exist in Sign, by design — confirmed with the user this isn't a gap to fill. `comment` requires `SOL` (column 1 exactly), so a comment can only ever occupy an entire line by itself, never trail after code. Discussed *why* at length (see below) before the user redirected to "what did you actually feel writing real Sign code" — worth remembering that pattern: the user sometimes wants the grounded/experiential answer, not the abstract-principle one, even when the abstract principle is also correct.

## Design discussion, not yet needing action

- **Why comments are SOL-column-1-only, not just "first non-whitespace char of any line":** the block/indent structure is determined by raw tab-count (`lexer.js`'s `markBlock`, computed before the grammar runs at all). If comments were allowed to start after arbitrary indentation, a comment line's own indentation would have to be excluded from indent/dedent-boundary computation — but that exclusion requires already knowing "this is a comment," which is a grammar-level (PEG lookahead) concern, not something the lexer's simple tab-counting pass can determine on its own. Restricting true comments to column 1 exactly sidesteps this chicken-and-egg problem entirely: a column-1 line has zero indentation by construction, so it can never be mistaken for a mid-block indent/dedent transition.
- **Why no inline comments specifically:** allowing "no closer found → comment" anywhere mid-line (not just at SOL) would mean a genuinely forgotten closing backtick (a typo, anywhere in real code) silently becomes "rest of line is a comment" instead of a loud syntax error. Restricting the no-closer-fallback to column-1-only means: everywhere else in the file, a missing closing backtick still fails loudly (a real parse error, catching the typo), and the "generous," easy-to-accidentally-trigger fallback behavior is confined to the one position (a line's very first character) where it's structurally unambiguous with real code.
