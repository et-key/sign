**The user's stated core motivation for creating Sign at all** (verbatim, 2026-08-06): "無名型だけど構造体型で、インスタンスには名前があるとかいうバカげた型の記述を辞めたいがために、Signを作っているのが本音" — the real reason Sign exists is to stop the "absurd" pattern (near-universal in mainstream languages: Java/C++/Rust/TypeScript `class`) where structures are fundamentally anonymous/structural, yet get an arbitrary *name* bolted onto the type declaration, and that name is then treated as load-bearing for type identity — even when two nominally-different types are structurally identical. This is not a minor preference; treat it as the thesis of the whole project.

**The Point/Vector2D thought experiment, worked through to its conclusion:**
- If `Point` and `Vector2D` are both defined as `{x, y}` with identical operations, do they have any actual difference? **No — and there is no mechanism in Sign for them to differ**, because "methods" aren't bound to type names at all; they're free functions dispatched purely by structural shape (`type_system.md` §6.2's `{x,y}` field-requirement matching). Any function usable with one is automatically usable with the other. This isn't "they happen to be equal" — structurally speaking they are *the same object with two names*, not two isomorphic-but-distinct things.
- Mathematically, the user pushed further: the only two questions math actually asks are **同型性 isomorphism** (do two *types* have a structure-preserving correspondence — a Hom-set/capability-set match) and **同値性 equivalence** (do two *values*, given that correspondence, coincide). "由来" (provenance — which constructor produced a value, i.e. nominal identity) is explicitly **not a mathematical category at all** — it's a pragmatic, opt-in engineering safety net. This maps directly onto Homotopy Type Theory's Univalence Axiom `(A ≃ B) ≃ (A = B)`: isomorphic types just *are* equal; there's no principled gap between "isomorphic" and "equal" for math to care about.
- Sign already encodes exactly this split, just not as two runtime operators: **isomorphism/structure-matching is a compile-time concern** (Pass1-3 type inference + `.st`'s structural field-requirement generation, §6.2) — invisible at runtime because if shapes don't match, field access just degrades to `__`, no explicit "shape check" needed. **Equivalence is `==`'s job alone** (already documented as "Hom集合の一致," which the user confirmed is *already* the right category-theoretic framing — matching Hom-sets is literally asking about isomorphism via Yoneda). `===`/`' !__` (provenance) is honestly a *third*, separate, non-mathematical axis — kept only as an explicit opt-in escape hatch (原理3's pattern: dangerous/nominal distinctions require an explicit, visible marker, never the default).
- Further refinement: what actually defines a "type" isn't data shape at all — it's the **set of supported operations** (trait/capability-based), which `type_system.md` §1 already states nearly verbatim ("Signにはtrait/interfaceに相当する宣言構文が存在しない...ある識別子に対して何が可能かという情報の集合は、その識別子を使うコードそのものがすでに語っている"). The user's framing: there is really only **one universal type** (`interface Math`), and every named "type" (Int, Point, List, ...) is just a particular subset of operations drawn from that one well. Data doesn't define the type; usage does.
- **Validating real-world precedent, unprompted by me:** JSON. Wire data carries no type name at all — two services can produce `{x:1,y:2}` calling it "Point" and "Vector2D" internally, and the receiver can't tell or care. When nominal distinction is actually needed on the wire, people bolt on an explicit `"type":"Point"` discriminator field — the *exact* same shape as `' !__`'s opt-in provenance check. TypeScript's structural (not nominal) `interface` typing is the direct academic response to this reality. The user's point: Sign isn't inventing an ideology, it's being honest about what JSON-scale software already does in practice.
- **On whether Pass1b's design repeats history's mistakes:** I raised the concern that Pass1b's "tests-as-generic-instantiation-evidence" mechanism (`compiler_pipeline.md` §6, debug builds run the `test` folder to trace call sites) could become the kind of "problem child" that Hindley-Milner constraint solving or C++ template metaprogramming became. The user's sharp correction: **it won't repeat that history**, because it descends from a *different, already-validated* lineage — Kent Beck-era TDD/XP's stance that tests are the real specification and names/structure are disposable/refactorable, not the "declare more type annotations to help the inferencer" lineage that HM and templates belong to. Concrete evidence offered: Japanese enterprise codebases where class names are literally sequentially numbered (`Class047`) and require an external glossary to decode — proof that nominal naming's promised semantic value is *already* routinely abandoned in practice, propped up by exactly the kind of out-of-band "provenance dictionary" that `.st`/`' !__` make official and explicit instead of ad-hoc.

**How to apply:** When working on Sign's type system, do not propose nominal-typing features (distinguishing structurally-identical types by name) as a *default* behavior — that's the thing the entire project exists to reject. `' !__`/`===` (provenance) stays a deliberate, narrow, opt-in exception, not a co-equal third pillar. Frame `==` as testing isomorphism-then-equivalence (Hom-set/capability match, then value coincidence), not "field comparison" — the latter is just what capability-matching happens to reduce to for plain data records. If asked to add trait/interface *declaration* syntax, remember §1's stance: the absence is deliberate, capability requirements are meant to be inferred from usage, not declared.

## Concrete fix that came out of this discussion (2026-08-06): Pass1b multi-argument positional bug

While reviewing Pass1b's known limitations in light of the above (specifically whether its rough edges are the "TDD-lineage" kind of problem or something more mundane), found and fixed a real, mundane bug: `pass1b.js`'s `collectCallsites` only ever looked at `apply[fnName, arg]` — a *single* apply level. For a multi-argument call like `g 10 $inc` (which resolves to the apply-chain `apply[apply[g,10],$inc]`), the old code matched only the *inner* `apply[g,10]`, meaning it always collected the **first** argument only, regardless of which position the generic parameter (`@ref`-referenced) actually occupied. A generic parameter in position 2+ would silently get the *wrong* argument's category attributed to it.

Fixed by adding `collectApplyChain` (same logic as `pass2.js`'s `applyChainInfo` / `interpreter.js`'s `collectApplyChain`) to walk the chain to its root and collect the full positional argument list per call site, then having `specializeGenericParams` select `argNodes[paramNameList.indexOf(paramName)]` instead of blindly using the single collected node. Verified directly via `collectCallsites`'s return shape (not through `specializeGenericParams`'s `categories`, because `$`-prefixed arguments — required to pass a Lambda as plain data without triggering `compose` instead of `apply`, see `coproduct_resolver.md`'s `apply : g x ? g x` note — always report category `"Atom"` regardless of position, so category-based comparison can't distinguish "right position" from "wrong position"; only inspecting the actual collected `argNodes` array proves it). 2-arg and 3-arg cases both confirmed correct positional ordering. Zero regressions (existing single-arg tests unaffected, since position-0-with-length-1 is a no-op case for the new logic).

**Still explicitly not attempted:** mutually-recursive generic function specialization (`type_system.md` §5 itself calls this "future work") — not touched, no reason to think it's needed yet.

## Spec addition, same session: struct field layout must be sorted by name, not declaration order

Follow-on from the type-philosophy discussion above: the user noted that struct field access is, underneath the "Hom-set equality" story, just offset+size arithmetic (RISC reality, 原理2's "本音"). This surfaced a real gap — if physical field *offsets* are assigned in raw declaration order, then `[x:1,y:2]` and `[y:2,x:1]` would be `==`-equal (same Hom-set, order doesn't matter for structural comparison per `type_system.md` §6.2) but could have *different* physical memory layouts (x at offset 0 vs offset 4) — a mismatch between mathematical equivalence and physical layout. The user's resolution, connecting to a "JS's original values" precedent (object properties are conceptually an *unordered* map — only arrays have meaningful order; modern JS's `Object.keys()` partially reflects this by sorting numeric-like keys ascending regardless of insertion order, per `OrdinaryOwnPropertyKeys`): **canonicalize field layout by sorting field names**, not by declaration order. Added as a new `[!IMPORTANT]` note in `documents/ja-jp/impl/memory/stack_abi.md` §7.1 (structs/alloca section) — this hasn't been implemented anywhere (no Pass4/codegen exists at all yet), it's a spec-only addition for when that backend eventually gets built.

**How to apply:** if/when Pass4 (codegen) is ever implemented, struct/Dict field offset assignment must sort by field name first — don't just walk fields in AST/declaration order. This is now a documented, settled rule, not an open question.

## New formal principle added, same session: `0_design_principles.md` 原理6

The whole type-philosophy arc above (Point/Vector2D → isomorphism vs equivalence vs provenance → trait-as-usage-not-declaration → struct/enum both emergent) crystallized into a genuinely new numbered design principle, added as **原理6：積も和も、構造的等価性から自然に生える** (`0_design_principles.md`, now 6 principles not 5 — the intro line and checklist were both updated too). Core claims now canonical:
- No dedicated "is-isomorphic" operator needed — a successful method call across two values *is* the proof of shared Hom-set (isomorphism), the same way TDD treats a passing test as the real specification. Only `==` (equivalence) is needed as a user-facing operator.
- Product types (struct/Dict) and sum types (enum) are **not** two separately-designed primitives — both emerge from "structural typing + `==`'s Hom-set semantics." The existing explicit enum sugar (`#RGB : Red | Green | Blue`) is now framed as a zero-cost special case of a more general phenomenon (any set of values sharing a common successfully-callable interface implicitly partitions into sum-type-like classes), not a bespoke feature.

**Closing epigraph added to 原理6** (the capstone line of this whole arc, user's own words, verbatim): "挙動が型であって、型が挙動を完全に邪魔することはない" (behavior is the type; the type never gets in the way of behavior) — "まさにやりたかったことだ" (this is exactly what I wanted to do). Added as the opening blockquote of 原理6 in `0_design_principles.md`, ahead of the technical isomorphism/equivalence explanation. If this project's type-system direction is ever in question, this one line is the tie-breaker: type system = optional, advisory, codegen-safety-helper; never a gate on behavior.
