- `__` を言語から追放し、単位は `_` だけで書く。
- alpha の JavaScript のうち、演算子の表と、前処理・lexer・構文は役に立つので持ってくる。
  その先の意味解析に入る前に、利用者に確かめる。

## alpha（c3b203fc）との違い

- **文法**：`unit = "_"`。alpha は `unit = "__" / "\x00"` と `hole = "_"` の2つだった。
  - `_` は字面を1つの形（`"_"`）で返す。読みは書いた位置で決まり、それは意味解析が見る。
  - 書いた `_` は穴にならない。穴の綴りは `!_`（前置 `!` と `_` の2語で返る）で、書いた `_` はいつも印である
    （下の「決まったこと」、2026-10-21）。alpha は `_` を穴に読んでいた。
  - `__` は識別子（`<__>`）として読む。
  - 単位の2つ目の綴り `\x00` も外した。alpha の `.js` を探した範囲では、これを作る側はどこにも無く、
    ソースに生の NUL を書くと黙って単位に読む穴になっていた。alpha1 では構文エラーになる。
- **演算子の表**：命令の綴り（`asm` 欄）と、`NOT_YET`・`NOT_AN_INSTRUCTION` の名簿は持ってこなかった。
  どれも機械の側の話で、意味解析より後で要る。構文の欄は alpha の表と 56 行とも同じである。
- **文書との食い違い**：`documents/{ja-jp,en-us}/impl/syntax/grammar.pegjs` はまだ `__` を単位に持っている。
  演算子表・穴の脱糖・match_case の文書にも `__` が残っている。`documents/ja-jp/impl/build/preprocessor.md` は、
  字下げのブロックの置き場所と定義の終わりの空行の規則をまだ持っていない。
  - 穴の綴り（2026-10-21）について、次の文書が古い綴りのまま（ja-jp と en-us の両方）。
    - guide の Hole：`guide/README.md` の `_` の行（「Hole（部分適用のプレースホルダ）」、`f _ 3 = $p0 ? f $p0 3`）と、
      `guide/reference.md` の「部分適用と Hole (`_`) / Unit (`__`)」。穴は `!_` で、既定値の無い関数の `f _ 3` は
      カリー化として同じ値になるが、既定値のある関数では断る（G15）。
    - `guide/example.sn` の `id : _`。恒等射は `id : !_` で、`_` は印（値）である。

## 決まったこと

- **古い `__` は、ただの識別子のまま**（利用者 2026-10-17「古い `__` はただの識別子のままでいい（10-14 の決定どおり）」）。
  名指しで断らない。前段はそう読んでいる。
- **`0u0000` は単位ではなく、ただの文字**で、`0uXXXX` という書き方の基準点である（`0u0041` は `0u0000 + 0x41`）。
  次の3つの法則から出る（利用者 2026-10-17「うん、とてもいい。」）。
  - A 単位律：`_ + \a = \a + _ = \a`
  - B 文字は Int と同じ扱いで、違うのは入出力のときだけ
  - C 文字は位置：文字 − 文字 → Int（距離）、文字 ± Int → 文字
  - `0u0000` が `_` だと、`\a - 0u0000` が A では `\a`、C では 97 になって割れる。U+0000 のビットを単位の印に
    使っていた（niche）のは機械の側の表し方で、法則ではなかった。

- **括りには「括り」の印を1つ付ける**（利用者 2026-08-05「カッコの意味って統一されているから種類を問うていない」、
  2026-10-17「その通り」）。`[...]`・`{...}`・`(...)`・`[]` は、どれも `["\"BRACKET_\"", 行の配列]` で返る。
  印が無かったときは、括りの中身と行が同じ形の配列で、根からの深さでしか見分けられなかった。
- **値や語のすぐ後ろの字下げは、余積の項にしない**（利用者 2026-10-17「これを余積の項と扱うと、ブロックと余積が
  混ざる場合がある、もし続けて余積の右辺だと言いたい場合、tabの後に空白が必須。」）。前の行の余積を続けるなら
  TAB の後に空白を置く（`inc` の次の行の `\t 5` は `inc 5`。括りを渡すときも同じ）。
  - ここから出した前段の読み（利用者に確認中）：字下げのブロックは、中置の意味を持つ演算子（`:`・`?` を含む）の
    右にだけ置ける。値や語、前置・後置にしかならない演算子（`$`・`!!`・`!`・`##`・`###`）で終わる行の下で字下げを
    深くしたら、前処理が名指しで断る（`block-after-value`）。
  - 前置にも中置にもなる綴り（`-`・`~`・`#`・`@`）は、前の行の末尾で空白に区切られているので中置と読む。前処理は
    演算子とブロックの間に空白を1つ置く（置かないとブロックに密着して前置と読まれていた）。
  - この読みだと、ガイドの次の書き方が断られる。
    - 構造体の拡張（`#Mob : MyGame~` の下に欄）：**廃止**（利用者 2026-10-18「構造体の拡張は廃止できる」）。
      構造体に型の名前を持たせる考えから来た形で、構造体はひとつひとつが実体、型は演算が満たす法則である
      （利用者 2026-09-17「構造体は、構造体という型だと言い切ってるのがSign」）。
    - ブロックの中だけの取り込み（`io@~` の下に `say Hello World`）：**関数で書く**（利用者 2026-10-18「案Aが良いね！」）。
      関数の本体を範囲にし、取り込んだ物を関数に当て、使う名前は仮引数で受ける。`[say]`・`[say ~rest]`・`[~rest]`
      のどれでも書ける（利用者 2026-10-18）。IO は関数がする（「構造体でIOを書こうなんて愚の骨頂」「関数でのIOはキレイだった」）。
    - ブロックの中の欄の読み（`myGreet` の下に `'greet`）：**分解して受ける関数で書く**（利用者 2026-10-18「合ってるけど、
      面倒なら何か特殊な糖衣構文を作ってもいいかもね。そこまで面倒だと思わないなら、その方法が良いと思う。」）。
      読むのは `greeting : [greet world] ? (greet ' welcome) world`、書き換えは組み直し（list_model.md §5.3.1）。
      糖衣は作らない（同じ射に綴りが2つ付く）。
    - alpha の試験の「字下げの1行は器の値」（`[+]` の下に `1 2 3`）：まだ確認中。
  - 意味解析で直すこと：構造体の上書き（`p~ [k : v]~`）は、いちばん外では構造体の合併になるのに、欄の値の中では
    同じ式が List と読まれ、alpha は「greet が Struct と List で衝突」と断る。置き場所で型が割れている。合併の法則を
    どこでも同じに当てれば、入れ子の書き換えも上書きで書ける。
- **いちばん外の定義が字下げのブロックで終わったら、空行を1行置く**（利用者 2026-10-17「関数ブロックの終了かつ、
  関数定義の終了／構造体ブロックの終了かつ構造体定義の終了／に空行を1行入れることが必須。」「ブロックの深さが
  変わるものは、空行を入れなくても判別できるはず。」、深さ0に戻る所だけで良いかに「その読みで合ってる。」）。
  - ブロックの途中の深さの変わり目、ブロックの中の定義の終わり、1行で書き終えた定義、仮引数のブロックの後に
    `?` の行が続く所には要らない。ファイルの終わりは、空行が無くても定義の終わりとして扱う。
  - 空行が無いまま、続きの行でない次の字下げ0の行が来たら、前処理が名指しで断る（`definition-end-blank-line`）。
    0列目の続きの行（` * 3` や `+ 2`）は定義の続きである。空行を置いた後の続きの行をどうするかは未決（今は、
    alpha からの決まり「空行を越えてつなぐ」のとおり定義につながる）。
  - ブロックの中の空行と、1行の定義どうしの間の空行は読み捨てる。行頭のコメントの行は空行に数えない。
  - 定義かどうかは、いちばん外の行に括りの外の `:` があるかで見る。だから値の定義（`n : 1 +` の下に字下げ）にも要る。
  - 括りで行をまたいだ定義（`p : [` … `]`）は字下げのブロックではないので、今は求めていない。
- **穴の綴りは `!_`、書いた `_` はいつも印**（利用者 2026-10-21「これ、holeが _ じゃなくて !_ と書くべきなんじゃないか
  という事」。主の Claude の「穴を !_、書いた _ はいつも印、で仕様を書き直していい？」に「それでいい。 / そうすることで、
  デフォルト引数の呼び出しは f _ 3 などの _ で呼び出せることになる。」）。読みは `docs/coproduct_spec.md` §3.5。
  - 既定値の無い関数の `f _ 3` は、今までどおりカリー化（`a ? f a 3`）である（同日「もちろん、デフォルト引数をもって
    なければ、Qua圏の法則と同型で、 f _ 3 がカリー化を意味することが出来る。」）。`f !_ 3` も同じ木で、`add 1 !_` は `add 1`。
  - 並びの最後の `_` は「ここで終わる」印：足りなければ `_`、飽和なら評価する（`add 3 _` は `_`、`add 2 3 _` は 5）。
  - 値だけの並びの `_` は消える（`1 _ 2` は `1 2`）。`!_` 1つは恒等射（括らずに書く）、`||!_||` は `[~x] ? ||x||`。
    括った `[!_]` は恒等射ではなく、否定の点なし（下）。
  - 決まっていない3つは、名指しで断る（同日「未決の3つ（go !_ xs、点なしの前置・後置の綴り、既定値のある関数の種類）は
    名指しで断っておいて。」）：`go !_ xs`（G13）、`[-_]`・`[_!]` などの前置・後置の点なし（G14）、既定値のある関数に
    書いた `_`（G15）。前置・後置の点なしは同じ日に答えが出て（下）、G14 は廃止した。
- **前置・後置の点なしは `_` で書く**（`[-_]`・`[!_]`・`[!!_]`・`[_!]`。利用者 2026-10-21「多分、既存の前置、後置を _ で示す
  記法で意味が衝突するのは ! だけだね。」。主の Claude の「前の `_` の綴りに戻して、R30 は外す。`[!_]` は恒等射のまま。否定の
  点なしは無くす（`!` は手で書かない、補の比較で書く、という 02:37 の筋）。綴りは1種類になる。」に「これがよさそうだね。 /
  その方が統一的に扱えると思う。」、続けて「これで以前のとおり !_ や _! がそのまま使えるね。」）。答えた道のうち「`[!_]` は
  恒等射のまま。否定の点なしは無くす」の所は、同じ日の次の言葉（下の「[!_] は否定の点無しにしないの？…」）で改まった。
  読みは `docs/coproduct_spec.md` の §2 と R30（廃止）、Q32。
  - guide の `[!_] 2 < 3`（en-us は `[!_] (2 < 3)`）・`[_!] 5` と、ja-jp `guide/reference.md` の「前後に `_` をつけて表現します」は、
    そのまま正しい。`[-_] 5`・`inc [-_] 5`・`[* 2,] [-_] 1 2 3` の `[-_]` も単項の点なし（関数）である。
  - 括った `[!_]` は否定の点なしで、恒等射は括らない `!_`（同日「[!_] は否定の点無しにしないの？ 恒等射なら括らなくていい。」）。
    否定の点なしを残すのは「確かに、出来る限り補の比較で書いてほしい気持ちはあるけど、多分使う人が違和感を持つと思う。」から。
    `(!_)` も括りなので同じ。2行以上の括りの中の `!_` の行は、今までどおり恒等射。
  - `_` は、書いていない被演算子の口の印と読む（主の Claude の読み。前置・後置の印は隣に何かが要る）。書いた `_` はいつも
    印、と食い違わない。
  - 同じ日に一度決めた、定義されていない名前を被演算子に書く綴り（`[-a]`、R30。利用者「僕は未定義の識別子なら何を当てても
    成り立つという書き方が良いと思っている。」と、主の Claude の提案への「良い提案だね！ / その方向で行こう！」）は廃止した。
    `_` の綴りで足り（ぶつかるのは `!` だけで、それも括るかどうかで分かれる）、綴りが1種類になるからである。`[-a]` は、名前 a に
    値の印を当てた項の括り（a が定義されていなければ値で、information は普通の文面）に戻った。`_` を断っていた G14 も廃止した。
  - `$`・`@`・`#`・`~` の点なしと、`[$_,]`・`[-_,]` のような写像（利用者「[$_,] に存在価値があるかどうか？ / も大事かもね。」）は、
    同じ日に答えが出た（下の項、`docs/coproduct_spec.md` の Q33）。
- **2項演算の点なしは、モノイドの域になる物だけ畳む**（利用者 2026-10-21「2項演算は左から畳んでいい、この時、畳んじゃいけないものは、
  モノイドの域になってない。」）。`[op] x1 … xn` は、`x1 op … op xn` を演算子表の結合の向きどおりに並べた物と同じ（同日「[^] は中置と
  同じく右から畳む。[op] x1 … xn は演算子表の結合の向きどおりに並べた物と同じ。」）。読みは `docs/coproduct_spec.md` の R31。
  - 畳むのは、算術の `+`・`-`・`*`・`/`・`%`・`^`（`^` だけ右から。`-`・`/`・`%`・`^` は「これは、強引だけど畳んでいい」）、ビットの
    `||`・`;;`・`&&`、論理の `|`・`&`・`;`（「[&] a b c / で c が返る。」、`;` は「入れていい」）、比較の `<`・`<=`・`=`・`>=`・`>`・`==`。
    利用者が名指ししていない `*`・`||`・`;;`・`&&` は、主の Claude が「モノイドの域」で畳む側に置いた。`+`・`|` はこの日の名指しは
    無いが、前から利用者の言葉がある（`[|]` は 2026-10-05「[&]は最も右を返し、[|]は最も左を返せばいい。つまり畳み込みも出来る」、
    `[+]` は `docs/coproduct_spec.md` の R31 の出どころ）。
    比較は、隣どうしが全部成り立てば一番右、外れれば `_`（「つまり比較点無しは一番右を返すか _」。`[<] 1 2 3` は 3）。中置の3項の
    連鎖（中央の項を返す）とは返す物が違う。
  - この項は決定の規則（主の Claude の案）。実引数が2項以上なら値。1項は、数ならその数（`[+] 5` は 5）、要素が全部値と見える
    List なら要素を畳む（`[+] [1 2 3]` は 6）。要素に関数が見える器（`gs : 1 , inc` の `[&] gs` は inc）と中身の見えない値（裸の
    仮引数・適用の結果）は、畳んだ結果が関数になりうるので、種類を決めずに断る（確かめで見つかった黙った誤答を直した）。
    実引数に書いた `_` は中置の被演算子と同じに読む（`[+] 1 _ 3` は 4、`[&] 1 _ 3` は `_`）。これは、案内の `[+] 1 __ 3` が `__`
    （利用者の裁定 2026-10-05、完全性公理）なのと割れていて、利用者にはまだ確かめていない。
  - 前置・後置の点なしは値の演算子（`-`・`!`・`!!`・後置の `!`）だけで、`$`・`@`・`#`・`~` には作らない（主の Claude の問いに
    「良いと思う。」）。`,` を付けた `[-_,]`・`[!_,]`・`[!!_,]`・`[_!,]` は `[* 2,]` と同じ要素ごとの写像（同日「前置・後置の点なしにも , を
    付けて、[* 2,] と同じ要素ごとの写像と読む。」）。`[$_]` は今までどおり値 `$_` の括りで、`[~_]`・`[@_]` などは点なしではなく断る。
- **畳まない2項の点なしは、素の2引数の関数と同じに読むが、おすすめはしない**（畳まないのはビットシフトと get・set（利用者
  2026-10-21「ビットシフトとget set は 畳めないね。」）、`!=`・`!==`（「だね」）と、主の Claude が畳まない側に置いた範囲。主の
  Claude の「素の2引数の関数と同じに読む、でいい？」に「同じに読んでいいけど、おすすめは出来ないという方向で良いと思う。」）。
  `[<<] 1 4` は `1 << 4`、`[<<] 1` は右の口を待つ関数、`[<<] 1 4 2` は余り。get・set（`[']`・`[@]`・中置の `[#]`）は何を引いたか・
  何をしたかが決まらないので種類を決めない。「おすすめは出来ない」は断らずに information（`pointfree-not-folded`）で見せる。
  get・set を `[']`・`[@]`・中置の `[#]` と読むのは主の Claude の読みで、足りた適用の種類と information の形は決定の規則（主の
  Claude の案）。読みは `docs/coproduct_spec.md` の R32。
