# Sign Language Design Motivation

## Why Build Sign?

In short:

> **"A language for AI to write bare-metal code."**

---

## 1. Target Audience

- **Primary User**: AI (Large Language Models and Code Generation Systems).
- **Secondary User**: Human engineers reviewing AI-generated code.

AI systems:
- Naturally manipulate mathematical and category-theoretic structures.
- Prefer deterministic semantics without runtime exceptions.
- Favor minimal syntax without syntactic ambiguity.
- Require static hardware safety verification during compilation.
- Need to generate code capable of running without an Operating System (Baremetal).

Sign addresses all of these requirements.

---

## 2. Why Baremetal?

Sign possesses an independent stack non-reliant on the C ecosystem:

- Describes BIOS/UEFI boot sequences directly in language options.
- Manages FPU and SIMD hardware initialization states at the type level.
- Allocates stack memory directly for data execution.

Code generated by AI can run directly on OS-less baremetal hardware.

---

## 3. Design Philosophy and AI Affinity

| Sign Design Property | Benefit for AI Code Generation |
|---|---|
| **Zero Reserved Words** | Eliminates reserved word collision risks; arbitrary identifiers evaluate to `__`. |
| **Unit (`__`) Propagation** | Deterministic Unit propagation without runtime exceptions. |
| **Syntax-Derived Types ($O(n)$)** | Instant linear-scan type inference. |
| **Execution Layer (`layer`) Constraints** | Structurally blocks hardware misuses (e.g. `Float` literals in `layer < 2`). |
| **Alloca-First Model** | Heapless closures and currying specialization. |

---

## 4. Human-AI Collaboration

- **AI**: Generates Sign code ensuring mathematical and category-theoretic correctness.
- **Human**: Defines architecture/intent and reviews output.
- **Compiler**: Catches hardware and type mismatches statically via layer rules.
