# Sign言語 型システム仕様

## 1. 設計原則：型は演算子と構文から自明に決まる

Sign言語の型システムには以下の根本的な性質があります。

> **型はデータに付与されるラベルではなく、演算子と構文木の形状から一意に決定される。**

これにより、**Hindley-Milnerのような型変数の導入・制約ソルビング・単一化は一切不要**であり、型はASTを辿るだけで確定します。

> [!NOTE]
> HMとの差はあくまで「制約ソルビングを行わない」ことであって、「走査が常にO(n)線形である」
> ことではない。識別子のカテゴリ解決（§5 Pass 1a）は依存グラフ上の不動点計算になり、
> ジェネリック仮引数の具体化（§5 Pass 1b）は呼び出しグラフに対する処理になる。
> どちらも型変数を持たず、解くべき制約集合も生成しない。

> **型は宣言される対象ではなく、コードが問題を解くために実際に行った操作（生成・使用）の反映である。**
>
> Sign には trait / interface に相当する宣言構文が存在しない。これは機能の欠落ではない。
> ある識別子に対して何が可能か（どのフィールドにアクセスできるか、どの演算が通るか）という
> 情報の集合は、その識別子を使うコードそのものがすでに語っている。`.st` はこの情報を
> 「宣言」するのではなく、コードから静的に「読み取って書き写す」だけの存在である。
> 型注釈の構文が存在しないのは簡略化ではなく、**型がコードの影である以上、注釈する対象が
> 最初から無い**という設計上の帰結である。

---

## 2. 型の階層（2レイヤー構造）

Sign の型システムは、独立した2つのレイヤーで構成されます。

### Layer 1: 構造型（Structural Type）

スペース演算子のセマンティクスを決定するための型。**構文から一意に決定される**。

| 構造型 | 定義 |
|:---:|---|
| `Lambda` | `?` 演算子を含む式、または部分適用を生成するブラケット式 |
| `Atom` | それ以外のすべての値・式（数値・文字列・リスト・Unit など） |

**Layer 1 の決定規則（構文から直読み）：**

```text
x y ? body          → Lambda  (`?` があるから確定)
[+ 2]               → Lambda  (部分操作のブラケット)
[f]                  → Lambda  (f だけを含むブロック。中身のカテゴリがそのまま出る。
                                アドレス化ではない——それは `$` の仕事、§3.5 参照)
$expr                → Atom    (Address。`$`は常に「アドレスという値」を返すだけの操作であり、
                                中身がLambdaかAtomかを問わない)
@expr                → 参照先の圏を継承（下記参照）

42                  → Atom    (数値リテラル)
`hello`             → Atom    (文字列リテラル)
x + y               → Atom    (算術演算の結果)
[1 2 3]             → Atom    (値のブラケット)
__                  → Atom    (Unit値)
```

> [!IMPORTANT]
> **`$`/`@` の非対称性**
>
> `$expr` は常に `Atom(Address)` を返す。凍結対象が関数（`$map_lazy`）であろうとデータへの
> パス（`$[array ' 0]`）であろうと、`$` 自身がやっていることは「その式が指す場所のアドレスを
> 取る」だけであり、場合分けを必要としない。
>
> 一方 `@expr` は、そのアドレスの先に何があるか（呼び出し可能な `Lambda` か、ただの `Atom`
> データか）を継承する。これは `$` の時点では決まらず、`@` によって参照・強制されたときに
> 初めて意味を持つ。多くの場合は静的に一意に決まる（`@handler` で `handler` の定義が既知なら
> 構文から読める）が、`f : ref ? @ref 1 2 3` のようにジェネリックな仮引数を介する場合は
> 定義サイト単体では決まらない。この場合は Rust/C++ のモノモーフィ化と同様、**各呼び出し
> サイトで実引数の具体的な型を用いて `.ist` 上に具体化する**ことで解決する（呼び出しサイトの
> ない `#export` はコンパイルエラー。[`compiler_pipeline.md` §4](../core/compiler_pipeline.md#4-ist内部と-st公開の分離生成方針)参照）。

**識別子の場合：**
識別子の構造型は、その定義がある行の構文から決定します。`?` を含む定義は `Lambda`、それ以外は `Atom` です。

```text
f : x y ? x + y     → f は Lambda（arity: 2）
val : 42            → val は Atom
```

### Layer 2: Atom 内部型（Atom Subtype）

演算の意味（型変換）を決定するための型。`Atom` の内部分類。

| Atom 内部型 | 説明 | リテラル例 | 使用可能な layer |
|:---:|---|---|:---:|
| `Address` | アドレス（ポインタ）。**符号なし整数（uint）を含む**。GPRレベルで最初から同一のビット表現なので、独立した`Int`内部型は不要（§3.6参照） | `42`, `0x00`, `0xFF`, `$expr` | 0以上 |
| `Float` | 浮動小数点数。FPU（GPRとは物理的に別のレジスタファイル）を要するためAddressとは統合できない。**幅はターゲットのFPUが持つ最高精度が自動選択される**（下記NOTE） | `3.14`, `1.0`, `-0.5` | **2以上** |
| `String` | Unicode 文字列（`List(0u)` と同型） | `` `hello` ``, `\a`, `0u3042`（下記NOTE） | 0以上 |
| `Vector` | SIMDベクトル型 | `[1.0 2.0 3.0 4.0]`（ベクトル指定時） | **3以上** |
| `List` | 同一型の値の1次元配列。要素型を伴い `List(T)` と書く（下記NOTE） | `1 2 3`, `[1 2 3]` | 0以上 |
| `Struct` | **固定オフセットで並ぶ連続ブロック**。スロットごとに型が違ってよい。名前付きスロット（`[key : val]`）と連番スロット（`1, 2, 3`）は同じ構造で、名前の有無だけが違う（下記NOTE） | `[key : val]`, `1, 2, 3` | 0以上 |
| `Implicit` | **暗黙のアドレス（場所）**。要素型を伴い `Implicit(T)` と書く。`'`（添字・フィールド）・前置 `~`（持ち上げ）・前置 `#`（確保）が生む「書き込める場所」（下記NOTE） | `array ' 0`, `~list` | 0以上 |
| `Iterator` | **ストリーム（Pull型）**。要素型を伴い `Iterator(T)` と書く。`{start, step, end}` 相当の固定サイズ構造体であり、要素列はメモリ上に展開されない | `1 ~+ 2`, 裸の `~xs` | 0以上 |
| `Unit` | 単位元・空・無 | `__` | 0以上 |

> [!IMPORTANT]
> **`0u....` は `Address` ではなく `String`（Char）である。**
>
> `String ≅ List(0u)` と書いている通り、`0u` は `String` の**要素型**である。したがって
> `0u3042` は符号位置の数値 0x3042 ではなく**文字「あ」**であり、`\あ` と同じものを指す
> （[`guide/example.sn`](../../guide/example.sn) の `uni_a : 0u3042` も「Unicodeで 'あ' を表現」と説明している）。
>
> 同じ文字を指す2つの記法が別の型・別の値になっていると、**外部から届いた Byte 列を
> Char 列へ変換する境界**（[`value_representation.md`](../core/value_representation.md) §4）が型として書けない
> ——「入力が実は文字列である」ことを型で扱えなくなる。これが `0u` を `Address` に
> 含めない理由である。
>
> **U+0000 だけは例外で `Unit` である。** U+0000 は Char の値域から除外された niche であり、
> `__` そのものだからである（`value_representation.md` §3、[`system_semantics.md`](../core/system_semantics.md)）。
> アドレスリテラル `0x00`（0番地、`Address` の有効な値）とは別物なので混同しないこと。
>
> ```sign
> 0u0041      ` `A`（String）
> 0u3042      ` `あ`（String）
> 0u0000      ` __（Char の niche。Unit そのもの）
> 0x00        ` 0（Address。アドレス0番地）
> ```

> [!IMPORTANT]
> **リテラルの layer 制約**
>
> | リテラルの形式 | 型 | 許可 layer |
> |---|---|:---:|
> | 小数点なし：`42`, `0xFF`, `-1` | `Address`（uint含む、§3.6参照） | 0以上 |
> | **小数点あり**：`3.14`, `1.0` | `Float` | **2以上** |
> | SIMD型指定：`[1.0 2.0 3.0 4.0]` | `Vector` | **3以上** |
>
> `layer < 2` のコード中で小数点を含むリテラル（`3.14` 等）を使用すると
> **コンパイルエラー**になる。FPUが初期化されていない段階での浮動小数点演算を構造的に防止する。

> [!IMPORTANT]
> **`Struct` と `List` を分けるのは「要素の型が揃っているか」ではなく、
> 「Pass 4 が1つの命令テンプレートで済むか」である。**
>
> | 型 | メモリ配置 | アクセス | Pass 4 が出すもの |
> |---|---|---|---|
> | `List(T)` | **同一幅**セルの連続 | `base + i × sizeof(T)`、**`i` は実行時変数でよい** | 命令テンプレート**1つ**＋インデックス計算 |
> | `Struct` | スロットごとに幅も解釈も違いうる | `base + `**コンパイル時に確定したオフセット** | スロット**ごとに別命令**（GPR/FPU、幅も別） |
>
> `1 , \`abc\` , 2.5` はスロット0が GPR ロード、スロット2が **FPU ロード**——
> 物理的に別のレジスタファイルなので、1つの命令テンプレートでは扱えない。
> これが `List` にできない理由である。
>
> **この帰結として、多相な `Struct` への実行時インデックスは原理的にコード生成できない。**
> 添字が静的に確定していなければスロットの型が決まらず、命令が選べないためである。
>
> ```sign
> ` OK: i が実行時変数でよい（要素型が一つなので命令が決まる）
> list ' i
> ` OK: リテラルなのでオフセットも型もコンパイル時に確定する
> struct ' 0
> ` NG: スロットの型が決まらず命令を選べない
> struct ' i
> ```
>
> **したがって `'` の右辺にある識別子を「名前」と読むか「値（添字）」と読むかは、
> 左辺が決める。**
>
> | 左辺 | 右辺の識別子 | 例 |
> |---|---|---|
> | 名前付きスロット | **名前** | `d ' foo` |
> | 連番スロット・`List`・`String` | **値（添字）** | `xs ' i` |

> [!IMPORTANT]
> **名前付きスロットは「名前・連番・実データ」の三つを持つ。**
>
> 名前で引くのは右辺が識別子のとき、**連番（宣言順）で引くのは右辺が数値のとき**である。
> スロット数は `|s|` で取れる。
>
> ```sign
> point : [
>     x : 3
>     y : 4
> ]
> point ' x       ` 3   名前で引く
> point ' 0       ` 3   連番（宣言順）で引く
> point ' -1      ` 4   負の連番は末尾から
> |point|         ` 2   スロット数
> ```
>
> **連番は宣言順であって、物理オフセットの順（名前ソートの正規順、
> [`stack_abi.md` §7.1](../memory/stack_abi.md)）ではない。** 両者が食い違っても矛盾しない。
>
> ```sign
> point2 : [
>     y : 4
>     x : 3
> ]
> point == point2   ` 真   Hom集合の一致は宣言順を問わない
> point ' 0         ` 3
> point2 ' 0        ` 4   等しいのに違う値
> ```
>
> これは**正しい観測**である。`==` は Hom集合の一致であって**同一性ではない**
> ——同一性は `===` と `' !__`（コンストラクタ由来の確認）が担う（§6.2）。宣言順は
> `==` が比較していない別の性質であり、それを測って違う値が出ることは偽を主張しない。
>
> 連番スロット（`1 , 2 , 3`）は名前を持たないので、スロットを同定する手段が連番しか
> ない。「名前の有無だけが違う」とは、この三つのうち名前が欠けるということである。
>
> 名前付きスロットと連番スロットは同じ構造であり、違いは名前を持つかどうかだけである。
> したがって区別の基準は左辺の形にしか無い——右辺の構文（識別子かリテラルか）では決まらない。
> 連番スロットは「順序が意味そのもの」であり、変数で引けなければバイト並びを扱う手段に
> ならない。名前付きスロットへ実行時の添字を渡した場合は上の NG の通りであり、名前として
> 引かれてそのキーが無いため `__` に収束する。
>
> 物理レイアウトの詳細は [`stack_abi.md` §7.1](../memory/stack_abi.md) を参照。
> フィールドは宣言順ではなく**名前でソートした正規順**で配置される——`==` は Hom集合の
> 一致（§6.2）であり宣言順を問わないため、`[x:1, y:2]` と `[y:2, x:1]` が
> 「型としては同じなのに物理配置が違う」という食い違いを防ぐためである。

> [!NOTE]
> **本仕様は以前 `Dict`（辞書型）という名前を使っていた（2026-08-09 に `Struct` へ改名）。**
>
> 実体は「固定オフセットで並ぶ連続ブロック」であり、フィールド名はコンパイル時に
> オフセットへ解決されて Pass 4 には残らない。実行時のキー探索もハッシュも動的な
> 追加も存在しないため、「辞書」という名前は実体を表していなかった。
>
> この食い違いが際立つのが MMIO のレジスタマップである。C の構造体オーバーレイ
> （`typedef struct { volatile uint32_t CR, SR, DR; } UART_Type;`）に相当する記述は、
> Sign では名前付きスロットの `Struct` そのものであり、`UART ' DR` は
> ハッシュ引きではなくコンパイル時に確定したオフセットへのアクセスである。
>
> なお [`stack_abi.md`](../memory/stack_abi.md) は当初から `Struct / Dict` を同一物として
> 併記しており、両者を別の型として列挙していたのは本表だけだった。

> [!IMPORTANT]
> **`Implicit(T)`（場所）と `Iterator(T)`（ストリーム）は、`Address` とも `List` とも別の型である。**
>
> この2つは §4 の型シグネチャ一覧では既に使われていた（`'` が `Implicit` を返す、
> 前置 `~` が `List -> Implicit(List)`、`~+` 等が `Iterator` を返す）が、本表に
> 載っていなかった。ここで補う。
>
> | | 何であるか | 生む演算子 |
> |---|---|---|
> | `Address` | **値**としてのアドレス。GPR幅の第一級の値で、uint と同一のビット表現 | `$expr`（明示的なアドレス取得） |
> | `Implicit(T)` | **場所**（書き込める先）。値ではなく「そこに T がある」という参照 | `'`、前置 `~`、前置 `#` |
> | `Iterator(T)` | **ストリーム**。Pull型で、消費側が要求した時にのみ次の値を生成する | `~+` `~-` `~*` `~/` `~^`、裸の `~xs` |
>
> `$` が `Implicit(T)` を `Address` へ明示的に格上げする関係にある——
> `$[array ' 0] # 99` は「`'` が生んだ場所を `$` で第一級のアドレスにし、`#` で書く」と読める。
>
> **この2つが型として区別されて初めて、[`list_model.md` §2.4](list_model.md#24-リスト渡しeagerとストリーム渡しlazyの明示的区別) の
> 区別が型の上で成立する。**
>
> | 仮引数の形 | 受け取るもの | Layer 2 型 |
> |---|---|---|
> | `f : [x ~xs] ?` | 実体化された参照（複数を同時に保持できる） | `Implicit(List(T))` |
> | `f : x ~xs ?` | ストリーム（Pull型、同時アクセス不可） | `Iterator(T)` |
>
> [`0_design_principles.md`](../0_design_principles.md) 原理3 はこの2つを
> 「安全な既定（stream）／危険な明示的opt-in（参照渡し）」として並べており、原理4 は
> 「`[...]` 内での stream 型識別子の使用」を静的拒否ルールとして挙げている。
> **その拒否は、`Iterator` が型として存在して初めて強制できる。**
>
> 同時アクセスが必要になる具体例は、割り込み／DMA を伴う IO である。音声バッファと
> フレームバッファのように、外界に触れる複数の場所を**同時に生きた状態で保持する**には、
> Pull型のカーソル（`Iterator`）では足りず、`Implicit` が要る。
> `Implicit(T)` は最適化のための道具ではなく、ベアメタル記述の土台である。

> [!IMPORTANT]
> **`List` と `Struct` は「要素の型が揃っているか」ではなく「どちらの記法で作ったか」で決まる。
> そのうえで `List` は同一型であることを制約として要求する。**
>
> | 記法 | 型 | 要素の型 |
> |---|:---:|---|
> | スペース（余積）：`1 2 3` | `List(T)` | **揃っていなければならない**（違反はコンパイルエラー） |
> | カンマ（直積）：`1 , 2 , 3` | `Struct` | 要素ごとに違ってよい |
>
> つまり §2 の `List` の説明「同一型の値の1次元配列」は、**分類のための判定基準ではなく、
> `List` が満たさなければならない制約**である。混在した値を持ちたい場合は、カンマで
> tuple（`Struct`）だと明示する必要がある——原理3（緩い・危険なことは既定では書けず、
> より明示的な構文でのみ書ける）の適用である。
>
> 根拠はハードウェアにある。`List` は**固定幅要素の連続領域**であり、幅も解釈も異なる値が
> 混ざると配置しようがない。`Struct` は直積なので要素ごとに別の幅・別の解釈を持って当然である。
>
> **要素型は型に含まれる。** `List(Address)` と `List(Float)` は別の型であり、
> §2 が「`String` は `List(0u)` と同型」と書いているのはこの記法によるものである。
>
> 要素型の一致判定には §3.2 の**数値の昇格格子**をそのまま使う（次節の余積族テーブル参照）。
> `[1 2.5]` は `1` が昇格して `List(Float)` になり、エラーにはならない——算術で
> `5 + 1.5` を `Float` へ昇格させるのと同じ理屈であり、ここだけ書き直しを要求すると
> 一貫しないため。一方 `[1 \`abc\`]` は昇格先が存在しないのでコンパイルエラーになる。

> [!NOTE]
> **`Float` に `Float`/`Double` のような幅の区別は存在しない。**
>
> 3つの数値型はいずれも「そのターゲットにおける、その**レジスタファイルの幅**」を指す：
>
> | Layer 2 型 | 幅 |
> |:---:|---|
> | `Address` | ターゲットの GPR 幅 |
> | `Float` | ターゲットの FPU が持つ**最高精度**（自動選択） |
> | `Vector` | ターゲットの SIMD 幅 |
>
> これは下記の「幅クラスごとに実行時のビット表現はただ1種類しか無い」という原則の
> 直接の帰結である。`Address` が 32bit ターゲットで 32bit、64bit ターゲットで 64bit に
> なるのと同じ理屈で、`Float` も f32 しか持たないターゲットでは f32、f64 を持つターゲット
> では f64 になる。プログラマが幅を選ぶ構文は無く、選ぶ必要も無い。
>
> したがって [`build_system.md` §4](../build/build_system.md#4-コンパイル階層layerとリンク設定) の layer 表が
> `Float/Double` と併記しているのは「FPU が扱える形式」の説明であって、Sign の型が
> 2つあるという意味ではない。

> [!IMPORTANT]
> **Layer 2の統一原理：実行時は幅クラスごとに単一のビット表現しか無く、精緻化は静的（Pass 1〜3）のみ**
>
> `Address`が`uint`を包含する理由（GPRレベルで整数もポインタも同一のビット表現）と、
> `String`が`List(0u)`と同型である理由（要素幅が同じなら同一のビット表現）は、
> **同じ1つの原理の異なる現れ**である。Signには「実行時に区別されるプリミティブ型」は
> 存在しない。幅クラス（GPR幅=Address、FPU幅=Float、SIMD幅=Vector等）ごとに、実行時の
> ビット表現はただ1種類しか無い。「整数かポインタか」「文字列か数値のリストか」といった
> 区別は、すべてPass 1〜3だけが持つ静的な精緻化（refinement）であり、コード生成では
> 完全に消える（[`compiler_pipeline.md`§2](../core/compiler_pipeline.md#2-型システムの立ち位置建前としてのheapless本音としてのrisc固定長制約)「型は実行時ゼロコストの帳簿」参照）。
>
> ただし、**「実行時に消える」ことは「Pass 1〜3の判断が緩い」ことを意味しない**。むしろ逆で、
> 消えても安全なのは、消える前のPass 1〜3が「どのビット列をどう扱うか」という操作的意味
> （`+`が計算になるか`__`に収束するか§3.2、スペースがテキスト連結になるかリスト構築になるか等）を、
> 曖昧さなく静的に確定させ切っているからである。型の精緻化（Int/Address、String/List等）は
> 実行時の見た目には現れないが、Pass 1〜3の判断そのものには常に厳密に対応している——
> 「消える」と「厳密でない」は別の話である。

## 3. 型規則

### 3.1 スペース演算子の4分類（Layer 1 に依存）

Layer 1 の構造型が確定した後、スペース演算子は以下の4つのセマンティクスを持ちます。

| 優先順位 | 左辺 | 右辺 | セマンティクス | 型規則 |
|:---:|:---:|:---:|---|---|
| 10.3 | `Lambda` | `Lambda` | compose（合成） | `Lambda(A→B) → Lambda` |
| 10.2 | `Lambda` | `Atom` | apply（適用） | `Lambda(A→B) → B \| Lambda` |
| 10.1 | `Atom` | `Lambda` | apply_reverse（逆適用） | `Lambda(A→B) → B \| Lambda` |
| 10.0 | `Atom` | `Atom` | concat（連接） | `Atom → List` |

> [!IMPORTANT]
> スペースのセマンティクスは **Layer 1 の構造型が確定してから**決まります。
> 構文解析段階でこれを正確に決定するには、全識別子の構造型を事前に収集する「プリパス」が必要です（→ 5節参照）。

### 3.2 左辺優先ルール（Layer 2 に依存）

**左辺は、適用する規則を選ぶ（ディスパッチする）。**

```
規則(L op R) = 演算子の族 × typeof(L)
```

これは型注釈なしで動作する単相型推論であり、制約ソルビングを必要としません。

> [!IMPORTANT]
> **「左辺優先」で優先されるのは、型の伝播ではなく規則の選択である。**
>
> 本節は以前 `typeof(L op R) = typeof(L)`（結果の型は常に左辺の型）と述べていたが、
> これは**算術族でしか成り立たない**。実際には：
>
> - 余積（スペース）は `Atom Atom → List` であり、左辺の型は結果型にならない（§3.1）
> - `&` の型シグネチャは `(L -> R) -> (R \| __)` であり、**右辺**の型を返す（§4）
> - 比較演算子は `(L \| R \| __)` を返し、左右どちらを返すかは
>   左辺の**値**が算術単位元（`0`/`1`）かどうかで決まる（[`comparison.md`](comparison.md) §2.1）
>
> 全ての族に共通しているのは「左辺が規則を選ぶ」という一点だけである。算術族では
> 選ばれた規則の結果がたまたま `typeof(L)` と一致するため、それが全族の法則であるかのように
> 一般化されていた。

**族別の結果型：**

| 族 | 演算子 | 左辺が選ぶもの | 結果型 |
|---|---|---|---|
| 算術 | `+` `-` `*` `/` `%` `^` | 左辺の**型**が演算の意味を選ぶ（数値／String拒否／List操作） | 数値なら**昇格格子**、それ以外は下表 |
| 余積 | スペース（`concat`/`construct`/`push`/`unshift`） | 左辺の**型**がテキスト連結かList構築かを選ぶ | `String`（左辺String）／それ以外は `List` |
| 比較 | `<` `<=` `=` `>=` `>` `!=` | 左辺の**値**（算術単位元 `0`/`1` か否か）が返す側を選ぶ | `typeof(L)` または `typeof(R)`（数値なら昇格格子で揃う） |
| 構造比較 | `==` `!==` `===` | — （Scalarに限定されない、§4 NOTE） | `typeof(L)` |
| 論理・圏論 | `&` | 左辺の**Unit性**が短絡を決める | `typeof(R)` |
| 論理・圏論 | `\|` `;` | 左辺の**Unit性**が返す側を選ぶ | `typeof(L)` または `typeof(R)` |
| 単項 | 前置・後置 | — | §4 の個別シグネチャによる |

> [!NOTE]
> 上表に `\| __`（Unitとの直和）を併記していないのは、省略ではなく設計判断である。
> 完全性公理（§3.4）により**あらゆる関数適用**が、値返却型比較により**あらゆる比較**が
> `__` を返しうる以上、`\| __` は全ての式に付く環境条件であって、型が運ぶ情報ではない。
> Layer 2 の型は常に「その式が値を返したときの型」を指す（§3.3 が Unit 側の規則を担う）。

**算術族の型変換テーブル：**

左辺の型がまず「どの規則を使うか」を選ぶ。数値（`Address`/`Float`/`Vector`）が選ばれた場合のみ、
そこから先は下記の**昇格格子**が働く。

| 左辺型 | 演算子 | 右辺の扱い | 結果型 |
|:---:|:---:|---|:---:|
| 数値 | 算術 | 昇格格子（下記） | 昇格格子（下記） |
| `String` | 算術（`+`等） | **型エラー（`__`消去）** | `__` |
| `List` | `*` | 右辺 `Address` 回コピー | `List` |
| `List` | `^` | 右辺 `Address` 回次元を上げてコピー | `List` |
| `List` | `/` | 右辺 `Address` 個のチャンクに分割 | `List` |
| `List` | `+` `-` `%` | **型エラー（`__`消去）** | `__` |

**数値の昇格格子（Numeric Promotion Lattice）：**

| 左 ⊕ 右 | 結果 |
|:---:|:---:|
| `Address` ⊕ `Address` | `Address` |
| `Address` ⊕ `Float` | **`Float`** |
| `Float` ⊕ `Address` | **`Float`** |
| `Float` ⊕ `Float` | `Float` |
| いずれか `String` | **`__`**（型エラー、**両方向**） |

> [!IMPORTANT]
> **数値は降格せず、常に精度の高い側へ昇格する。**
>
> `5 + 1.5` は `Float` の `6.5` であって、`Address` の `7` ではない。左辺が `Address` でも
> 右辺の `Float` を丸めて捨てたりはしない。
>
> これは「左辺が規則を選ぶ」（本節冒頭）と矛盾しない——左辺が選ぶのは**どの族の規則を使うか**
> （数値演算か、String拒否か、List操作か）であって、数値族の内部でどちらの幅に揃えるかは
> 昇格格子が決める。
>
> **理由**：Sign は数学表現・形式手法を扱える記法であることを目標にしている。その記法において
> `+` が黙って小数部を捨てるのは、**記法が意味について嘘をつく**ことになる。
> 精度を落としたい場合は、後述の通り `Address` を構造的に要求する演算子
> （`'` によるインデックス、ビット演算、`@` による参照外し）の側で落ちる。
>
> なお `Address` と `Float` の混在は **layer 2 以上でしか発生し得ない**（Float リテラルは
> `layer < 2` でコンパイルエラーであり、[`build_system.md` §4.2](../build/build_system.md#42-layer-間インポートルール) により
> 自身より高い layer のコードはインポートできないため、外から Float が入り込む経路も無い）。
> したがって昇格規則が layer によって分岐することはない。

> [!IMPORTANT]
> **除算（`/`）だけは `Address` 同士でも丸めが起きる。**
>
> `Address` ⊕ `Address` の `+` `-` `*` `%` は結果も整数だが、`/` は非整数を生じうる。
> このとき結果は **四捨五入（最近接、タイは 0 から遠ざける）** で `Address` に丸める。
>
> ```sign
> ` → 3   （2.5 → 3）
> 5 / 2
> ` → -3  （-2.5 → -3。0 から遠ざけるので -2 ではない）
> -5 / 2
> ` → 4   （3.5 → 4）
> 7 / 2
> ```
>
> この丸め方向は AArch64 の `fcvtas`/`fcvtau`（最近接、タイは0から遠ざける）に1命令で対応する。
> `Address` 同士の整数除算に限っては、切り捨てる `sdiv` の前後に符号に応じた補正
> （`a >= 0 ? (a + b/2)/b : (a - b/2)/b`）が必要になるが、除算命令自体のレイテンシに対して
> 追加分は小さく、除数が定数の2冪ならシフトに落ちて `(a + (1 << (k-1))) >> k` の +1命令で済む。
>
> **この規則は全 layer で共通とする。** layer によって切り捨てと四捨五入を切り替えると、
> 下位 layer のモジュールを上位からインポートしたときに同じソースが違う値を返すことになり、
> cross-layer import が意味論の地雷になるため（[`build_system.md` §4.2](../build/build_system.md#42-layer-間インポートルール)）。

**余積族（スペース）の型変換テーブル：**

| 左辺型・右辺型 | 扱い | 結果型 |
|:---:|---|:---:|
| **どちらかが** `String` | 両辺を文字列化して連結 | `String` |
| どちらかが `Unit` | 余積の単位元として素通し（`__ x = x`、`x __ = x`、§6.1） | もう一方の型 |
| それ以外 | List の要素として構築（要素型は下記の join） | `List(T)` |

> [!IMPORTANT]
> **空文字列（`` `` ``）は上の表の1行目に当たる。`Unit` の行ではない。**
>
> 空文字列と `__` は**値としては同じもの**である——零対象は一つしかなく、`String` の
> 終端は U+0000 の niche、すなわち Unit そのものだからである
> （[`value_representation.md`](../core/value_representation.md) §3・§4）。違うのは**型**だけである。
>
> したがって「テキストとして連結するのか、List を構築するのか」は値では決まらず、
> **型が決める**。これは `5 / 2` と `5.0 / 2` を型で分けたのと同じ構図であり、
> [原理2](../0_design_principles.md)の「型はゼロコストの帳簿」がそのまま働く場所である。
>
> ```sign
> `` 1 2 3        ` `123`   —— `` は「以降をテキストとして連結する」という宣言
> __ 1 2 3        ` [1 2 3] —— Unit は余積の単位元なので落ちる
> 1 2 3 ``        ` `123`   —— 位置は問わない（String は余積の吸収元、§3.2）
> ```
>
> **イディオムの範囲**: 空文字列は他の文字列とまったく同じに振る舞う、と読めばよい。
> `` `abc` [1 2 3] `` がテキスト連結ではなく List への追加になる（ブラケットが
> List を確定させるため 10.1/10.2 へ落ちる）のと同様に、`` `` [1 2 3] `` も
> List への追加になる。特別扱いは無い。
>
> なお List をテキスト化するときは**要素の描画を順に連結する**（`String ≅ List(0u)` で
> ある以上、区切り文字は入らない）。`1 2 3 \`abc\`` は `` `123abc` `` である。

> [!IMPORTANT]
> **`String` は余積の吸収元である。左辺に来たときだけではない。**
>
> `` `ab` 1 `` が `` `ab1` `` になるなら、`1 \`ab\`` も `` `1ab` `` でなければならない。
> そうでないと、**同じ演算子が引数の順序で挙動を変える**ことになる。
>
> これは §3.2 冒頭の「左辺が規則を選ぶ」の例外ではなく、より強い性質による：
> **あらゆる値はテキスト表現を持つため、`String` との join は常に存在する**
> （「レンダリングする」という全域の操作がある）。join が存在しない組み合わせだけが
> 下記の要素型エラーになるのであって、`String` はそもそもそこに入らない。

**要素型の join（`List` の同一型制約、§2）：**

余積で構築される `List` の要素型は、左右の要素型の join を取る。join は
**数値の昇格格子そのもの**であり、格子の外へ出る組み合わせには join が存在しない。

| 左要素 ⊕ 右要素 | join | 例 |
|---|---|---|
| 同じ型どうし | その型 | `1 2 3` → `List(Address)` |
| `Address` ⊕ `Float` | `Float`（昇格） | `[1 2.5]` → `List(Float)` |
| 数値 ⊕ `List`/`Struct`/`Struct` | **存在しない → コンパイルエラー** | `1 [x : 1]` |
| どちらかが未解決（`null`） | 判定しない（エラーにしない） | 仮引数経由など |

> [!NOTE]
> 要素型が静的に決まらない場合（仮引数を経由した値など、§2 の既知の制限）は
> **エラーにしない**。原理4 は「静的に決定可能な違反」だけを弾く原理であり、
> 決定不可能なものは実行時の自己責任の側に残る（原理2）。

> [!NOTE]
> 混在させたい場合はカンマで `Struct`（tuple）だと明示する：`1 , \`abc\`` は正当である。
> `List` を作ろうとして混ざった場合だけがエラーになる。

> [!NOTE]
> `String` は `List(0u)`（Unicode コードポイント列）と同型である。
> スペース（余積）による連結は可能だが、`+` 等の算術演算子はリストに対して効かないため `__` へ収束する。

> [!NOTE]
> 上表の `Address` は §2 の Layer 2 内部型（uint を包含する GPR 幅の型）を指す。
> 本節は以前 `Int` という語を使っていたが、**`Int` という Layer 2 型は存在しない**（§2 参照）。

### 3.3 Unit の型規則（非対称 Unit 伝播則と比較演算子の吸収則）

`__`（Unit）は演算子の種別によって以下の振る舞いを持ちます。算術演算子では左右非対称（左辺=吸収元、右辺=単位元）、比較演算子では**両辺とも吸収元**（`!=` のみ例外）となります。

圏論的構成（&, |, ;）における零対象:
  __ & x = __  /  x & __ = __    (積の終対象として吸収)
  __ | x = x   /  x | __ = x     (余積の初対象として素通し)
  __ ; x = x   /  x ; __ = x     (対称差の初対象として素通し)

算術演算子（+, -, *, /, %, ^）における非対称 Unit 伝播則:
  __ + x = __      (左辺の Unit はエラー伝播として「零射（吸収元）」になる)
  x + __ = x       (右辺の Unit は欠損値として「id射（素通し）」になる)

比較演算子（<, <=, =, >=, >）における吸収則:
  __ < x = __  /  x < __ = __    (比較対象が存在しない → 演算不成立 → __)
  例外: x != __ = x              (「X は Unit ではない」は論理的に真 → X を返す)

| 演算 | 種別 | `__` が左辺の場合 | `__` が右辺の場合 |
|:---:|:---:|---|---|
| `&`（AND）| 積（対称吸収） | 吸収元: `__ & x = __` | 吸収元: `x & __ = __` |
| `\|`（OR） | 余積 | 単位元: `__ \| x = x` | 単位元: `x \| __ = x` |
| `;`（XOR）| 余積対称差 | 単位元: `__ ; x = x` | 単位元: `x ; __ = x` |
| `+`, `-`, `*`, `/`, `%`, `^` | **算術演算子**（非対称） | 吸収元（零射）: `__ + x = __` | **単位元（id射）: `x + __ = x`** |
| `<`, `<=`, `=`, `>=`, `>` | **比較演算子**（対称吸収） | 吸収元: `__ < x = __` | 吸収元: `x < __ = __` |
| `!=` | **比較演算子（例外）** | 吸収元: `__ != x = __` | 単位元: `x != __ = x` |

算術演算子における**「右辺の Unit は単位元として無視される（`x op __ = x`）」**という仕様は、再帰関数などで可変引数（`~rest`）が尽きた際も、余分な終了条件を書かずに自然に計算が底打ちするように設計されているためです（比較演算子には適用されません）。

```sign
` 例: sum_list [1 2 3]
` 【注意】括弧が必須。算術演算子(+, precedence=13)はスペース/関数適用(precedence=10)より
` 優先順位が高い（先に結合される）ため、括弧無しの `x + sum xs~` は `x`と`sum`（関数値
` そのもの）を直接`+`で結合しようとし、意図と異なる結果になる。
sum : x ~xs ? x + (sum xs~)

` xs が空（__）のとき、sum __ は __ に崩壊するが、
` x + __ は「右単位元」として x を素通しするため、再帰が綺麗に終了する。
```


> [!NOTE]
> **`__`（単位元）と `[__ ]` / `[ __]`（恒等射）の区別**
>
> - `__` 単体は **Unit 値（Atom）** として振る舞い、吸収元として機能します。
> - `[__ ]` は静的脱糖により `$p0 ? __ $p0` → `$p0 ? $p0` と等価な**恒等関数（Lambda）**です。
> - `[ __]` は静的脱糖により `$p0 ? $p0 __` → `$p0 ? $p0` と等価な**恒等関数（Lambda）**です。
>
> これは Haskell における `mempty`（モノイド単位元）と `id`（恒等関数）の区別に相当します。

### 3.4 関数適用の完全性公理

> [!IMPORTANT]
> **Sign の関数適用には「完全性公理」が存在します。**
>
> **「引数のいずれかが `__`（Unit）である関数適用は、`__` を返す」**
>
> これは算術的な Unit 伝播とは独立した、言語の根本的なセマンティクス公理です。

```
∀f, f __ = __    （いかなる関数 f に対しても）
```

 この公理は「関数適用が完了したとみなされる条件」から導出されます。
Sign の関数仕様では、**引数が全て有効値（非 Unit）で評価しきられて初めて、その関数呼び出しは真（有値）とみなされます。**
引数に `__` が含まれる = 「評価しきれていない」= false（偽）= `__`。

```sign
f : x y ? x + y

` → 8      （完全評価）
f 3 5
` → __     （y が Unit → 完全評価でない → __）
f 3 __
` → __     （x が Unit → 完全評価でない → __）
f __ 5
` → __ （2 < 1 = __ → f 3 __ → __）
f 3 (2 < 1)
```

**デフォルト引数との連携：**
デフォルト引数を持つ関数は例外的に、`__` が渡された引数にデフォルト値を適用できます。

```sign
g :
    x
    y : x + 1
  ? x + y

` → 7   （y はデフォルト値 3+1=4 を使用）
g 3
` → 7   （y = __ → デフォルト値 4 にフォールバック）
g 3 __
` → __  （x = __ → デフォルトなし → 完全評価不能 → __）
g __ 5
```

### 3.5 高階関数と `$`/`@` による Lambda ↔ Atom 変換

Coproduct Resolver は余積の各要素を **Lambda** か **Atom** に分類してスペース演算子を解決します。
通常の関数は Lambda として分類されますが、**高階関数の引数として別の関数を渡すとき**、
同じ余積列に Lambda が複数並ぶと「関数合成（compose）」と解釈されてしまいます。

```sign
` g は Lambda パラメータ
apply : g x ? g x

` 問題: apply (add 3) 5 の余積を Resolver にかけると
` [Lambda(apply), Lambda(add3), Atom(5)]
`  → Priority 2: Lambda+Lambda → compose
`  → (apply ∘ add3)(5) ← 意図と異なる
```

**解決策: `$` 演算子で Lambda を Address (Atom) に降格する**

> [!NOTE]
> §2で確認した通り、`$` は入力がLambdaであろうとAtomであろうに関係なく常に `Atom(Address)` を返す。
> ここでは高階関数の文脈上、入力がLambdaであるケースを例に取っている。

| 演算子 | 変換方向 | 型カテゴリの変化 |
|:---:|---|---|
| `$` | Lambda → Address（一般には任意の式 → Address） | Lambda → **Atom** （Coproduct Resolver の対象として正しく扱われる） |
| `@` | Address → 参照先の圏を継承 | Atom(Address) → 参照先が `Lambda` なら呼び出し、`Atom` ならメモリ読み出し |

```sign
apply_five : f ?
    ` @f で Address を Lambda として呼び出す
    (@f) 5.0

high_order_result : apply_five ($(add 10.0))
` $(add 10.0) → Address(Atom)
` [Lambda(apply_five), Atom($add10)]
`  → Lambda + Atom → apply  ✓
```

この機構により、**高階関数の引数渡しは常に `$` を明示することで型カテゴリが Atom に確定し**、
Coproduct Resolver が曖昧さなく決定論的に解決できます。
`@` / `$` の対称性は C 言語の関数ポインタ（`&func` / `(*fp)()`）に相当しますが、
型注釈なしで Layer 1 分類を明示的に制御できる点が Sign 独自の設計です。

## 4. 演算子別型シグネチャ一覧

> **記法**: `L` = 左辺の型、`R` = 右辺の型  
> `Scalar` = String を**含まない** Atom（Number など）  
> `Atom` = String を**含む**スカラー  
> `Point` = 範囲の端点になれるもの＝**数値と1文字**（下記 NOTE）  
> `List` = `Array | Struct`（多相リストは `Struct`）  
> `Implicit` = 暗黙のアドレス（Implicit Address）

> [!NOTE]
> **範囲の端点（`Point`）は数値と1文字である。**
>
> 範囲は「点から点まで」を表すため、端点は点でなければならない。数値のほかに
> **文字**が端点になれる——文字は Layer 2 では `String` だが、範囲の端点としては
> 符号位置で数える点だからである。両端が文字なら結果は文字の並び、すなわち
> `String` になる（`String ≅ List(0u)` なので、文字の List は String そのもの）。
>
> ```sign
> 1 ~ 5        ` List:   [1 2 3 4 5]
> \a ~ \e      ` String: `abcde`
> \e ~ \a      ` String: `edcba`（降順）
> ```
>
> `List` と `Struct` は点ではないため端点にできない。ただし**停止はしない**——
> 点でないものを端点に置くことは「射が無い」ということであり、零対象を経由する射
> （零射）が常に存在する以上、結果は `__` である（[原理4](../0_design_principles.md)の
> 「型が合わないことは違反ではない」を参照）。静的に判定できた分は §5 Pass 3b が
> `range-endpoint-not-a-point` として理由を記録する。**多文字の `String`** が点で
> ないことは型では決まらない（`String` は文字数を持たない）ため、実行時に `__` へ落ちる。
>
> step を伴う派生演算子（`~+` `~-` `~*` `~/` `~^`）の端点は数値のみである。
> 文字に対する等差・等比の意味は定めていない。
>
> なお `~` の結果は**端点の型ではない**（列である）ため、§3.2 の左辺優先ルールの
> 対象外である。

| 記号 | 位置 | 型シグネチャ |
| :------: | :------: | ------ |
| `#` | 前置※ | `R -> Implicit(R)` |
| `##` | 前置※ | `R -> Implicit(R)` |
| `###` | 前置※ | `R -> Implicit(R)` |
| `:` | 中置※ | `(Identifier -> R) -> R` |
| `?` | 中置※ | `(List -> R) -> Lambda(R)` |
| `#` | 中置※ | `(Address -> R) -> (Address \| __)` |
| `;` | 中置 | `(L -> R) -> (L \| R \| __)` |
| `\|` | 中置 | `(L -> R) -> (L \| R \| __)` |
| `&` | 中置 | `(L -> R) -> (R \| __)` |
| `==` | 中置 | `(L -> R) -> (L \| __)` |
| `!==` | 中置 | `(L -> R) -> (L \| __)` |
| `,` | 中置※ | `(L -> R) -> List` |
| ` ` | `Atom \| List` 中置 `Lambda` | `((Atom \| List \| __) -> Lambda) -> (List \| Lambda \| __)` |
| ` ` | `Lambda` 中置 `Atom \| List` | `(Lambda -> (Atom \| List \| __)) -> (List \| Lambda \| __)` |
| ` ` | `Lambda` 中置 `Lambda` | `(Lambda -> Lambda) -> Lambda` |
| ` ` | `Atom \| List` 中置 `Atom \| List` | `((Atom \| List \| __) -> (Atom \| List \| __)) -> (List \| __)` |
| `~` | 中置 | `(Point -> Point) -> Iterator -> (List \| String)` |
| `~+` `~-` `~*` `~/` `~^` | 中置 | `(Scalar -> Scalar) -> Iterator` |
| `<` `<=` `=` `>=` `>` `!=` | 中置 | `(L(Scalar) -> R(Scalar)) -> (L \| R \| __)` |
| `+` `-` | 中置 | `(L(Scalar) -> R(Scalar)) -> L` |
| `*` `/` `%` | 中置 | `(L(Scalar) -> R(Scalar)) -> L` |
| `^` | 中置※ | `(L(Scalar) -> R(Scalar)) -> L` |
| `\|...\|` | 囲み | `L(Scalar) -> L` |
| `'` | 中置 | `(L -> R) -> Implicit(Atom \| List \| Lambda) -> Deref(Implicit -> (Atom \| List \| Lambda))` |
| `@` | 中置※ | `(R -> L) -> Implicit(Atom \| List \| Lambda) -> Deref(Implicit -> (Atom \| List \| Lambda))` |
| `<<` `>>` | 中置 | `(L(Address \| Register) -> Number) -> L` |
| `\|\|` `;;` `&&` | 中置 | `(L(Address \| Register) -> Scalar) -> L` |
| `!` | 後置 | `Number -> Number` |
| `~` | 後置 | `Deref(Implicit -> (List \| Struct \| Atom))` |
| `@` | 後置 | `Implicit(Struct) -> Deref(Implicit -> Struct)` |
| `~` | 前置※ | `List -> Implicit(List)` |
| `!` | 前置※ | `R -> (R \| __)` |
| `$` | 前置※ | `Any -> Atom(Address)` （§2参照。入力のLambda/Atomを問わず常にAddressを返す） |
| `@` | 前置※ | `Atom(Address) -> (Lambda \| Atom)` （参照先の圏を継承。静的に一意でなければ呼び出しサイト単位で具体化） |
| `!!` | 前置※ | `Scalar -> Scalar` |

> [!NOTE]
> `=` 等の比較演算子の対象は `Scalar` に限定されるため、`[1 2 3] = [1 2 3]` のようにリスト等の非スカラーを対象とした場合はコンパイルエラー（型エラー）になります。リストや構造体の比較には `==` を使用してください。
>
> **比較演算子の返値に関する重要ルール**：
> - 2項比較の場合、左辺が算術単位元（`0` または `1`）の場合だけ右辺を返します（それ以外は左辺を返します）。
> - 3項までの連鎖比較（`L < C < R`）は、構文解析時に単一のASTノード（`ChainCompare`）として扱われ、同一演算子での連鎖を条件に**真となる場合、中央の変数項（`C`）を返します**。

### 4.1 アクセス系演算子と `Float`（数値の降格が起きる唯一の場所）

§3.2 の通り、算術族では数値は**昇格しかしない**。`Float` が `Address` へ落ちるのは、
**`Address` を構造的に要求する演算子の側**だけである（なお §3.5 の「`$` による Lambda →
Address の降格」は Layer 1 のカテゴリ変換であり、ここで言う数値の幅の降格とは別の話である）。実例を洗うと、float から `Address` への
変換が現実に必要になるのは「**添字にしたい**」場合であって、「**番地にしたい**」場合ではない：

```sign
` 正規化座標から画素位置へ
pixels ' (u * width)
` 時刻からサンプル位置へ
samples ' (t * rate)
` 値からヒストグラムのビンへ
bins ' (value / bin_width)
```

浮動小数点で番地そのものを計算する動機は存在しない。番地は `base + index * stride` という
整数演算で作られる。float から出てくるのは常に**位置**であり、位置は整数でしか存在しない。
この非対称が、以下の規則の根拠である。

| 式 | 挙動 | 根拠 |
|---|---|---|
| `list ' 1.5` | **四捨五入して添字**（`fcvtas` 1命令） | 位置は整数でしか存在しない。丸め方向は §3.2 の除算と同じ |
| `dict ' 1.5` | **キー参照**（`1.5` というキーがあるか） | Struct の添字は位置ではなくキー。丸めの問いが立たない |
| `` `abcd` ' 1.5 `` | **四捨五入して文字**（→ `` `c` ``） | String は `List(0u)` と同型（§2）なので List と同じ規則 |
| `@1.5` | **四捨五入して参照外し** | 番地は整数でしか存在しない。読みなので復旧可能 |
| `1.5 # v` | **コンパイルエラー** | 生アドレスへの**破壊的**書き込み。実例が存在せず、ほぼ確実にバグ |
| `$1.5` | `1.5` を保持する無名一時オブジェクトのアドレス | `$` は**変換しない**。オペランドを評価してそのアドレスを取るだけ（§2） |

> [!IMPORTANT]
> **`Address` を構造的に要求する位置に `Float` が来たら、常に四捨五入する。例外を作らない。**
>
> `'`（添字）・`@`（参照外し）・ビット演算のいずれも同じ規則であり、AArch64 では
> `fcvtas`/`fcvtau` の1命令に落ちる。原理1（RISC as-is）が要求しているのは
> 「単一命令に落ちること」ではなく（`^`・`!` のように多命令へ落ちる演算子は許容されている）、
> **ソースを読めば命令列が読めること**である。同じ `'` が添字の型によって
> 1命令にも10命令にもなる設計は、命令数の多寡ではなくこの予測可能性を壊すため採らない。

> [!IMPORTANT]
> **`'` は「左辺が規則を選ぶ」（§3.2）がコンテナ型に対して働く例である。**
> 同じ `'` が、左辺が List なら位置指定、Struct ならキー参照として振る舞う。
> `1.5` という添字の意味（丸めるべき位置か、キー名か、どちらでもないか）は左辺の型だけで決まる。

> [!NOTE]
> **補間（interpolation）は `'` に組み込まない。通常の関数として書く。**
>
> 分数位置での読み書きには、随伴なペアをなす有用な操作が実在する：
>
> - 読み：隣接要素の線形補間（GPU のテクスチャサンプラが行っているもの）
> - 書き：隣接要素への重み付き分配（scatter。Wu のアンチエイリアス線分、splatting、勾配蓄積）
>
> 補間写像は線形写像であり、分配はその転置にあたる。この対称性自体は正しい指摘である。
> しかし線形補間は補間ファミリー（nearest / linear / cubic / windowed sinc …）の
> 最も単純な一員に過ぎず、実務ではどれを使うかを選びたい。`'` に一つを焼き付けると
> 選択肢を奪ううえ、`arr ' (n * 0.5)` のように意図せず `Float` が紛れ込んだ場合に
> **エラーも出ないまま、10倍遅く、値も違う**という最悪の失敗をする。
>
> 原理6 の通り、構造は専用演算子ではなく「適用が成功すること」で示されればよい。
> 補間と scatter は関数のペアとして書けば、随伴関係も保たれたまま、
> 補間の種類もプログラマが選べる。

> [!NOTE]
> `1.5 # v` だけをコンパイルエラーにして `@1.5` を許すのは、原理3（危険はデフォルトでは
> 書けず、明示的な opt-in でしか書けない）の読み/書き非対称の適用である。読み間違いは
> 値が変になるだけだが、書き間違いはメモリを壊す。原理3 の表が既に「仮引数部での `#`（Output）は
> **禁止**」という非対称を持っており、原理5 が `$__ # expr` を「言語破壊」と名指ししているのも
> 同じ温度感である。

## 5. 型決定アルゴリズム（コンパイラ実装指針）

### Pass 1a: 識別子テーブルの収集と呼び出しサイトの記録（プリパス）

ソースを走査して、全識別子の構造型とアリティを収集します。

**識別子の構造型は「右辺式のカテゴリ」である。** §2 の表が定めている通り、Lambda を生む形は
`?` だけではない——部分操作のブラケット（`[+ 2]`）も compose（Lambda∘Lambda）も Lambda である。
したがってカテゴリの決定は、右辺式に対する再帰的な判定になる。

```
category(expr):
  トップレベルに `?` がある            → Lambda(arity = count_params(left_of_?))
  部分操作のブラケット `[+ 2]` / `[!_]`  → Lambda                      (§2の表)
  丸括弧・単一要素ブラケット `[f]`        → category(中身)               (透過)
  `L R` で L・R とも Lambda            → Lambda                      (compose、§3.1)
  識別子                              → category(table[識別子])       (エイリアス)
  アリティ不足の適用 `f 1`              → Lambda(arity = 残りのアリティ)  (部分適用)
  それ以外                            → Atom(atom_type = infer_literal_type(expr))

for each definition `name : expr`:
  table[name] = category(expr)
```

> [!IMPORTANT]
> **自己参照・相互参照は `Atom` に倒す。**
> `f : f` や `a : b` / `b : a` のような循環は、解決中フラグで打ち切って `Atom` とする。
> 値としても循環しており、`Lambda` と見なす根拠が無いためである。
>
> **この規則により、Pass 1a は純粋な線形スキャンではなくなる。**
> 識別子のカテゴリが他の識別子のカテゴリに依存するため、実体は依存グラフ上のメモ化付き
> 不動点計算である。これは Pass 1b が既に明示している逸脱（呼び出しグラフに対する処理で
> あり単純な線形走査ではない）と同じ性質のものであり、Sign の型システムが Hindley-Milner
> と異なる点は「走査が線形であること」ではなく、**型変数を導入した制約ソルビング・単一化を
> 一切行わないこと**である（§1・§7.1 参照）。
>
> なお、参照された時点で解決する遅延方式を採れば、この再帰は定義行の順序に依存しない
> ——「前方参照を含む全識別子の構造型が確定する」という下記の性質は保たれる。

このプリパスにより、**前方参照を含む全識別子の構造型が確定**します。

同時に、**全ての呼び出しサイトもこの同じ走査で記録**します（どの関数が、どんな型の実引数と共に適用されているか）。

```
for each coproduct application `f arg1 arg2 ...`:
  callsites[f].push({ argCategories: [category(arg1), category(arg2), ...] })
```

> [!NOTE]
> このプリパスの出力は **`.ist`**（内部向け、全識別子を含む）としてコンパイラのプロセス内メモリ上にのみ構築されます。
> ディスクへは永続化されず、増分コンパイル用のキャッシュとしても使いません（セキュリティ上の理由。詳細は
> [`compiler_pipeline.md` §4](../core/compiler_pipeline.md#4-ist内部と-st公開の分離生成方針)を参照）。
> このうち `#`/`##`/`###` でexportされた識別子だけが、ビルド完了時に **`.st`** ファイルとしてディスクに
> 書き出され、外部モジュールから型情報を参照可能になります。

### Pass 1b: ジェネリックな仮引数の具体化（呼び出しグラフへの処理、線形ではない）

> [!IMPORTANT]
> Pass 1a のカテゴリ解決だけでは、`f : ref ? @ref 1 2 3` のようなジェネリックな仮引数（参照先が
> LambdaかAtomかが定義サイト単体では決まらないもの）の構造型を確定できない。Pass 1a が辿るのは
> 定義の右辺式（と、そこから参照される他の識別子）だけであり、**実引数として何が渡されたか**は
> 定義側からは見えないためである。Pass 1b はこれを補うために呼び出しグラフを辿る。
>
> 定義の依存グラフを辿る Pass 1a に対し、Pass 1b は呼び出しグラフを辿る——どちらも単純な線形走査
> ではないが、型変数を導入せず制約集合も作らない点は共通である（§1 参照）。

このプリパスは Pass 1a で「保留（generic）」と印を付けた識別子だけを対象にする。

```
for each `pending` (generic) function f:
  if callsites[f].length === 0:
    if f is exported (#/##/###): compile error (具体化できないエクスポート)
    else: discard (デッドコード、.ist/.stに現れない)
    continue

  for each distinct argCategories signature in callsites[f]:
    specialize f's body using argCategories
    table[f + '$' + signature] = { category: resolved, ... }
```

具体化された関数の本体が**さらに別のジェネリック関数を呼んでいる**場合は連鎖する。呼び出しグラフの位相順で
処理するか、不動点に達するまで反復する必要がある（相互再帰するジェネリック関数同士の扱いは未解決。
本節は将来の検討事項とする）。

この具体化は「パラメトリック多相」（下記参照）とは別物である点に注意。`@ref` は参照先が
`Lambda`か`Atom`かで**生成されるコード自体が分岐する**（呼び出し命令 vs メモリ読み出し命令）ため、
型変数では表現できず、呼び出しサイトごとに別々の実体（`.ist`上のエントリ、必要なら`.st`も別々）として
具体化する必要がある。

### Pass 2: 余積（スペース）の解決

完全な識別子テーブルを用いて、スペース演算子のセマンティクスを確定し、ASTを2分木に変換します。

```
for each space between L and R:
  catL = table[L].category or infer_from_syntax(L)
  catR = table[R].category or infer_from_syntax(R)
  
  if catL == 'Atom'   and catR == 'Lambda': → apply_reverse
  if catL == 'Lambda' and catR == 'Atom':   → apply
  if catL == 'Lambda' and catR == 'Lambda': → compose
  if catL == 'Atom'   and catR == 'Atom':   → concat
```

**Pass 1 を先に完了させることで、この判定に曖昧さがなくなります。**

### Pass 3: Layer 2 型の伝播

左辺優先ルール（§3.2）に従い、各ノードの Atom 内部型を伝播させます。左辺の型は
「結果の型」ではなく「**適用する規則**」を選ぶことに注意（§3.2 の族別テーブル参照）。

```
typeof(L op R):
  leftType =
    L is a literal      → typeof(L)
    L is an identifier  → table[L].atom_type
    L is an expression  → typeof(recursive(L))

  演算子の族 × leftType から、§3.2 の族別テーブルで結果型を引く
    算術族       → 数値なら昇格格子、String/List+算術 は __
    余積族       → leftType が String なら String、それ以外は List
    比較族       → leftType（左右は同族のScalarを要求）
    構造比較族   → leftType
    論理・圏論族 → `&` は typeof(R)、`|`/`;` は typeof(L) または typeof(R)
```

### Pass 3b: `__` へ収束する経路の静的記録

Pass 3 は結果型を伝播させる過程で、**式が `__` へ収束すると静的に判明した箇所と、その理由**を
`.ist` へ記録する。

`__` は零対象であり、あらゆる崩壊が同じ `__` へ潰れる。これは代数として正しく、
実行時にはこの一様性こそが価値である（オーバーヘッドゼロの判定・収束）。しかし
**「なぜ潰れたか」は互いに全く異なる**：

| 収束の理由 | 出典 |
|---|---|
| 完全性公理（引数のいずれかが `__`） | §3.4 |
| 比較が偽 | §3.3 |
| 算術族の型不一致（String × 数値） | §3.2 |
| `Scalar` 以外への比較演算子の適用 | §4 NOTE |
| 未定義識別子の収束 | [`unit.md`](../core/unit.md) §0.1 |
| インポート失敗 | §6.1 |
| 空リスト・空文字列（`__ = []`） | [`unit.md`](../core/unit.md) |
| Struct に存在しないキーの参照 | §4.1 |

Sign の真理は Boolean ではなく、**値そのものを証拠として返す**（原理6：「同じ関数が複数の値に
対して成功裏に呼べること自体が、それらが Hom 集合を共有することの直接の証拠になる」）。
真の側は witness を運ぶのに、偽の側が何も運ばないのでは非対称である。この非対称を、
**値ではなく帳簿（`.ist`）の側で**埋めるのが本節の役割である。

> [!IMPORTANT]
> **記録するのは Pass 1〜3 が静的に判定できた分だけであり、実行時には一切残らない。**
> 原理2（型は実行時ゼロコストの帳簿）をそのまま真理にも適用する。
> リリースビルドの成果物には、収束理由を運ぶコードもデータも含まれない。
> ユーザーから見れば「操作したが何も起きなかった」だけであり、例外で落ちることも、
> 不正アクセスが起きることもない——零対象が全てを吸収するため、そもそも壊れた値を
> 参照外しする経路が存在しない。

> [!NOTE]
> **実行時側の対応物は [`unit.md` §7.3](../core/unit.md#73-デバッグ環境におけるunit追跡と可観測性-unit-traceability--dynamic-payload)（Unit Traceability & Dynamic Payload）である。**
>
> | | 担当 | 対象 |
> |---|---|---|
> | 本節（Pass 3b） | コンパイル時 | 静的に `__` と判明する式 |
> | `unit.md` §7.3 | 実行時（デバッグ層のみ） | 実際に発生・伝播した Unit の因果軌跡 |
>
> 両者は補完関係にある。静的に決まる分は Pass 3b が先に潰し、実行時の値に依存して初めて
> 決まる分だけがデバッグ層のペイロードに載る。どちらもプロダクションビルドには残らない。

## 6. `.st` ファイル（型シグネチャファイル）

`SignType` 形式（`.st`）は、Sign に `->` 演算子を追加した型シグネチャ専用の構文です。

```signtype
` 関数の型シグネチャ
f : (Number -> Number) -> Number

` ジェネリックな関数（Atom 型パラメータ）
map : (Lambda -> List) -> List

` 識別子の Atom 型
pi : Number
greeting : String
```

.st` ファイルの役割：
1. **外部モジュールの型情報提供** — 別ファイルの識別子を参照する際の型根拠（ソースが手元にない配布シナリオを含む）
2. **型の自己文書化** — 実装（`.sn`）と型（`.st`）の分離による可読性向上

> [!NOTE]
> `.st` は Pass 1 の高速化（キャッシュ）を目的としない。同一ファイルの `.sn` を再コンパイルする際は
> 毎回 Pass 1 を最初から実行し、非公開識別子も含む `.ist` をメモリ上に作り直す（§5 参照）。
> Sign のビルドはコンパイル速度そのものを最優先の設計目標としていないため、この単純さを優先する。

### 6.0 二種類の多相と `.st` での書き分け

`.st` は2つの異なる性質の多相を区別して表現する必要がある。

| 種類 | 例 | コード生成 | `.st` での表現 |
|---|---|---|---|
| **パラメトリック多相** | `identity : T -> T` | 型が何であれ**生成コードは1つ**で共通 | 大文字始まりの型変数（`T`, `U`）をそのまま使う |
| **アドホック多相（`@`分岐）** | `apply_five : ref ? @ref 5.0` | 参照先の圏によって**生成コードそのものが分岐**（呼び出し命令 vs メモリ読み出し命令） | 呼び出しサイトごとに別々のシグニチャとして具体化する（Pass 1b 参照） |

前者は型変数のまま`.st`に書いておけばよい（Rust の `fn identity<T>(x: T) -> T` のジェネリクスに相当し、
単相化の必要がない）。後者は`@`の参照先によってコードが分岐するため、型変数では表現できず、
Pass 1b（§5参照）が呼び出しサイトごとに具体化した実体として`.st`に複数のシグニチャを並べる。

```signtype
` パラメトリック多相：型変数のまま、1エントリで済む
identity : T -> T

` アドホック多相（@分岐）：呼び出しサイトごとに実体が分かれる
` [f g ? @f @g] のような apply_five 的な関数に、
` 呼び出しサイト1で (Lambda, Atom) の組が、呼び出しサイト2で (Lambda, Lambda) の組が
` それぞれ渡された場合：
apply_five$Lambda_Atom : Lambda(Number -> Number) Number -> Number
apply_five$Lambda_Lambda : Lambda(Number -> Number) Lambda(Number -> Number) -> Lambda
```

> [!NOTE]
> 具体化のキー（`$Lambda_Atom` 等）の命名規則は未確定。ここでは可読性のため引数の構造型を
> アンダースコア区切りで並べた仮の記法を使っているが、確定した記法ではない。

### 6.1 モジュールインポートと `__` 単位元の挙動

インポートは `ファイル名@~` の形で行います。インポートが成功すれば、エクスポートされた識別子が
現在のスコープに追加されます（Pass 1 がインポート先のファイルに対しても実行される）。

```sign
`add.sn
#add : [+]

`add.sn`@~
` → 3  （add は Lambda として解決される）
add 1 2
```

**インポートが失敗した場合：**

インポートが失敗した識別子は未定義となり、**未定義識別子の Unit 収束則**により `__` として評価されます。

```sign
` add.sn が存在しない場合
`add.sn`@~
` add は未定義 → add : __ （Unit 収束）

add 1 2
```

`add = __` のとき、Coproduct Resolver の処理では `__`（Unit）が**余積の単位元（初対象）として素通し**されます。

```
[Atom(__), Atom(1), Atom(2)]
  → Unit をフィルタ（単位元として消去）
  → [Atom(1), Atom(2)]
  → Atom + Atom → concat
  → [1, 2]  （リスト。クラッシュなし、ただし意図とは異なる値）
```

> [!IMPORTANT]
> **`__` の二つの役割は、式中の「位置」によって決まります。**
>
> | `__` の位置 | 圏論的役割 | 振る舞い |
> |---|---|---|
> | **関数の位置** (`__ x`) | 余積の**初対象**（単位元） | 引数を素通しにする |
> | **引数の位置** (`f __`) | 積の**終対象**（吸収元） | 全体を `__` に収束させる |
>
> これは同一の記号 `__` が零対象（Zero Object）の双対性として機能しているためです。
> 文脈（位置）によって始対象（initial object）と終対象（terminal object）の
> どちらとして振る舞うかが、一意かつ決定論的に解決されます。

### 6.2 コンストラクタ関数と `==` の意味論

> [!IMPORTANT]
> **`==` は常に純粋な構造比較（Hom集合の一致）であり、コンストラクタ名を一切参照しない。**
>
> 形状（使えるフィールド・演算の集合）が一致すれば、異なるコンストラクタ経由であっても `==` は真になる。
> これはバグではなく、「構造（Hom集合）がすべてを決める」という Sign の設計原則そのものである。
> コンストラクタ名は意味を伝えるための命名であって、`==` の判定には一切関与しない。
> コンストラクタ経由を区別したい場合は、後述の `' !__` を opt-in で明示的に使う。

#### コンストラクタ関数による struct の定義（`.sn` ファイル）

```sign
` Point 型 = Point というコンストラクタ関数
#Point : x y ? [
  x : x
  y : y
]

` インスタンス生成 = ただの関数適用
point1 : Point 1 2
point2 : Point 5 7
```

> [!IMPORTANT]
> **`?` の直後にインデントブロック（TAB）を使うと `match_case` 構文になる。**
> コンストラクタのように複数フィールドの値を返す場合は、必ず `[...]` ブロックで明示する。
>
> ```text
> ` ❌ match_case と衝突する（NG）
> Point : x y ?
>   x : x     ← パーサーが条件 `x`、結果 `x` と解釈してしまう
>   y : y
>
> ` ✅ [...]ブロックで明示（OK）
> Point : x y ? [
>   x : x
>   y : y
> ]
> ```

#### enum（直和型）のコンストラクタ

> [!IMPORTANT]
> **ペイロードなし enum の各バリアントは、C言語の `enum` と同様に、Pass 1 が自動的に異なる Int 定数（0, 1, 2, ...）を
> 割り当てる。「由来を静的に遡る」必要はない——値そのものが最初から区別されているからである。**

```sign
` Red=0, Green=1, Blue=2
#RGB : Red | Green | Blue

` Lambda<returns: Red>（id射）
Red   : !__
` Lambda<returns: Green>
Green : !__
` Lambda<returns: Blue>
Blue  : !__

col  : Red 0xFF

`型がRedであるため、colが返る
col === Red 0xFF
`型がRedであるため、 col === Green は__となる
col === Green 0xFF

```

これは RTTI ではない。RTTI は「値から型を後から問い合わせる」機能だが、これはただ
「定義時点で値そのものを別々にする」だけであり、Cの enum と完全に同格のゼロコストな静的解決である。
`col == Red` は単なる Int 比較になるため、`col` の由来を静的に遡れない場合（ファイルから読んだバイトや
ユーザー入力など、実行時ディスパッチ）でも正しく動作する。

#### コンストラクタ由来を明示的に確認する：`' !__`

`==` はコンストラクタ由来を見ないため、Point と Vector2D のようにフィールド形状が同じ値は
`==` で真になる。これは正しい挙動である。区別したい場合にのみ、`'` の右辺に `!__` を渡す。

```sign
p : Point 1 2
v : Vector2D 1 2

` → 真（p は Point 経由で静的に遡れる）
p ' !__ = $Point

`→ __（別コンストラクタ由来、または静的に遡れない）
p === v

`→ 真（値と構造が等しく、準同型と言える）
p == v
```

Pass 1 が束縛の右辺を静的に遡れる場合、`' !__` はそのコンストラクタの named binding アドレス
（`$Constructor` 相当）を返す。実行時分岐でどのコンストラクタを経由したかが確定するなど、
静的に遡れない場合は `__` を返す——「わからない」を「わからない」のまま伝播させるだけで、
誤った判定や実行時タグを持ち出さない。素の `__` を渡した場合は `'` の通常の Unit 吸収則の
対象のままであり、この機構とは無関係である。

> [!NOTE]
> これは型システムによる強制ではない。`.st` の情報提供と同じ立ち位置で、使うかどうかは
> プログラマの判断に委ねられる。コンストラクタを経由しない裸のリテラル（`[x:1, y:1]` 等）は
> 遡るべきコンストラクタを持たないため、`' !__` は常に `__` を返す。

#### enum バリアントの実行時識別（解決済み）

上記の自動番号付け（Cの enum と同様の異なる Int 定数割り当て）により、enum バリアントの識別は
普通の Int 比較に帰着する。

```sign
describe : col ?
  col === Red   : `red`
  col === Green : `green`
  `blue`
```

`Red`・`Green`・`Blue` がそれぞれ異なる Int 値として定義されている以上、`col == Red` は値の直接比較であり、
`col` の由来を静的に遡れる必要はない。実行時分岐でどのバリアントが渡されても（ファイルパース・ユーザー入力等）、
値そのものが別である限り正しく分岐する。

これにより、本仕様書が以前想定していた `!__`（id射）を使った enum 定義は不要になる。`!__` 自体は
`p ' !__`（コンストラクタ由来の確認）という別の用途で引き続き有効であり、enum の識別には不要だったということになる。

#### 配列（List of struct）

`[Point,]` は「コンストラクタ関数 Point をカンマ（直積）区切りの各グループに適用するコンビネータ」。
カンマ演算子 `,` を Point に置き換えて各行を構築する、Sign 独自の map パターン。

```sign
` [Point,] 1 2 , 3 4 , 5 6
`  → Point 1 2 , Point 3 4 , Point 5 6（3要素の Pointリスト）
points : [Point,] 1 2 , 3 4 , 5 6

` アクセス
` → 3（2番目の要素の x フィールド）
points ' 1 ' x
```

#### `.st` ファイルの役割（変更なし）

`.st` ファイルはコンストラクタ関数のシグネチャを記述する。コンパイラが `.sn` から自動生成する。
手書きの補完にも使える。

```signtype
` point.st — コンパイラが自動生成
Point : Int Int -> Point
```

#### 関数仮引数のフィールド要求も `.st` に自動生成する

仮引数には型注釈スロットがないが、本体が `'` でどのフィールドにアクセスしているかを
Pass 1 が集めれば、要求フィールド集合を自動生成できる。これは Hindley-Milner 型の
制約ソルビングではなく、識別子ごとにアクセスされたキー名を集合として集めるだけの単純な走査である
（本節末の NOTE の通り、別関数へのパススルーまで追う場合は再帰的な走査になる）。

```sign
distance : p1 p2 ?
  dx : p1 ' x - p2 ' x
  dy : p1 ' y - p2 ' y
  dx * dx + dy * dy
```

```signtype
` 自動生成される distance.st
distance : {x, y} {x, y} -> Number
```

`{x, y}` は「少なくとも x, y フィールドを持つ構造体」という構造的な要求であり、`' !__` が返す
ノミナルタグとは別レイヤの情報である。呼び出し側では、引数の `.st`（`Point : Int Int -> Point` 等）が
提供するフィールド集合と、要求集合の包含関係を確かめるだけで検証が完結する。

> [!NOTE]
> この検証は `.st` による情報提供であり、コンパイラによる強制（コンパイルエラー）にするかどうかは
> 別途の方針決定である。分岐でアクセスが変わる場合は使われうる全フィールドの和集合を要求とする。
> 別関数へのパススルーも含めて要求を伝播させるには、Pass 1 を前方参照を含めて再帰的に回す必要がある。

#### 命名規則まとめ

| 記法 | 場所 | 意味 |
|------|------|------|
| `#Point : x y ? [...]` | `.sn` | コンストラクタ関数の定義（型定義） |
| `Point 1 2` | `.sn` | インスタンス生成（関数適用） |
| `[Point,] 1 2 , 3 4` | `.sn` | Point のリスト（コンストラクタマップ） |
| `point` | `.sn` | インスタンス名（小文字） |
| `Point` | `.st` | コンストラクタのシグネチャ宣言（自動生成） |

## 7. ラムダの型解決

### 7.1 なぜ `?` の型は右辺で解決可能か

**Sign のプログラムは演算子の連鎖だけで書かれる。**

この制約が型推論を自明にする。すべての演算子は型シグネチャを持ち、演算子の適用は型変換である。したがって、式全体の型は「演算子連鎖を辿るだけ」で決定できる。制約ソルビングは不要。

```sign
f : x y ? x + y
```

| ステップ | 式 | 型 |
|---|---|---|
| 1 | `x` | `Scalar`（Pass 1 で算術演算子から仮定） |
| 2 | `y` | `Scalar`（同上） |
| 3 | `x + y` | `+` の型シグネチャ: `Scalar × Scalar → Scalar` |
| 4 | `?` の右辺 | `Scalar` |
| 5 | `f` | `Lambda<returns: Scalar>` |

**これが Hindley-Milner と根本的に異なる点**：  
HM は型変数を導入して制約ソルビングを行うが、Sign は演算子テーブルが型変換の完全な定義を持つため、**未知数を立てずに**演算子連鎖をなぞるだけで型が確定する。単一の式についてはこの通り連鎖1回で済む（識別子のカテゴリが他の識別子に依存する場合の全体の計算量については §1・§5 Pass 1a を参照）。

---

### 7.2 `|` 演算子の二重性：値レベル vs 型レベル

`|` 演算子は2つの意味を同時に持つ：

| 観点 | 動作 |
|---|---|
| **値レベル** | 短絡評価：左辺が `__` でなければ左辺、`__` なら右辺 |
| **型レベル** | 直和（union）生成：`T₁ \| T₂` という和型を作る |

---

### 7.3 `match_case` の返値型は自然に enum になる

`match_case` は `&`/`|` チェーンにデシュガーされる。各 arm の型は演算子連鎖から自明に決まり、`|` チェーン全体の型はそれらの**直和（coproduct）**になる。

```sign
classify : x ?
  x < 0 : `negative`   ` arm 1: String
  ` arm 2: Int（Unit と同型の 0）
  x = 0 : 0
  `positive`            ` arm 3: String（デフォルト）
```

デシュガー後：

```sign
classify : x ?
  x < 0 & `negative` |
  x = 0 & 0          |
  `positive`
```

各 arm の型：`String`, `Address`, `String`  
返値型：`String | Address | String` = **`String | Address`**（enum）

> [!IMPORTANT]
> **enum は新しいプリミティブではない。**
> `match_case` の `|` チェーンから自然に導出される直和型そのものが enum である。
> Sign は専用の `enum` 構文を一切必要としない。

---

### 7.4 関数は指数対象である

圏論的に、関数型 `A → B` は指数対象 `B^A` として表される。

Sign の関数は：

| 関数の種類 | 返値型 | 指数対象表記 |
|---|---|---|
| 単一式関数 | `T` | `T^Arg` |
| match_case 関数 | `T₁ \| T₂ \| ... \| Tₙ` | `(T₁ \| T₂ \| ... \| Tₙ)^Arg` |

コンストラクタ関数も同じ：

```sign
` Red=0, Green=1, Blue=2
#RGB : Red | Green | Blue

` Lambda<returns: Red>（id射）
Red   : !__
` Lambda<returns: Green>
Green : !__
` Lambda<returns: Blue>
Blue  : !__

` match_case → 返値型が直和（String）になる例
` Lambda<returns: String>
#classify : col ?
  col == Red   : `red`
  col == Green : `green`
  `blue`
```

Sign における「成功/失敗」のパターンは、データ付き variant ではなく **Unit 伝播** で実現する。
成功時は値、失敗時は `__` を返し、呼び出し元が `|` でフォールバックするのが Sign のイディオム。

```sign
` ✅ Sign の Result パターン（Ok/Err は不要）
#parse : src ?
  ` 成功: src を返す、失敗: __ に収束
  valid src & src | __

` 呼び出し元
result : parse input | `default`
```

---

### 7.5 `$`/`@` 演算子と Lambda 型の解決

`?` 演算子により Lambda の返値型が静的に確定するため、`$`/`@` の意味が一意に決まる：

```text
#func : x ? x + 1             ` Lambda<returns: Scalar>
$func → Atom(Address)           ` §2の通り、$は常にAddressを返す
@$func → Scalar               ` @が参照先（funcのLambda値）を継承し、遅延評価を駆動

handler : 0xFF00              ` Atom(Address)（? なし）
@handler → Deref(Address)     ` 参照先がAtomなのでメモリ読み出し（関数呼び出しではない）
```

**`@_` の型解決ロジック（参照先の圏を継承）：**

```
@Atom(Address → 参照先がLambda<returns: T>)  → T      （評価駆動）
@Atom(Address → 参照先がAtom)                → Deref  （メモリ読み出し）
@__                                            → __     （Unit の読み出し = Unit）
```

Pass 1 の識別子テーブルにより、各識別子が Lambda か Atom（Address 等）かは多くの場合 **コンパイル時に確定している**。`@` が「遅延評価の駆動」か「メモリ読み出し」かは実行時ではなく静的に決まる。ただし `f : ref ? @ref ...` のように引数経由で参照先が変わる場合は、§2で述べた通り呼び出しサイト単位の具体化で解決する。

## 8. 型システムの完全性

以上の仕様により、Sign の型システムは以下の性質を持ちます。

| 性質 | 状態 |
|---|:---:|
| Layer 1（Lambda/Atom）の静的決定 | ✅ 右辺式のカテゴリから決定（§5 Pass 1a） |
| スペース演算子のセマンティクス確定 | ✅ Pass 1+2 で完全 |
| Layer 2（Atom 内部型）の静的決定 | ✅ 左辺が族ごとの規則を選ぶ（§3.2） |
| 参照（`Implicit`）とストリーム（`Iterator`）の区別 | ⚠️ 型としては定義済み（§2）。仮引数形（`[x ~xs]` / `x ~xs`）への割り当ては未実装 |
| 前方参照の解決 | ✅ Pass 1（プリパス）で解決 |
| 型変数・制約ソルビング | ✅ 不要（未知数を立てない。計算量については §1 参照） |
| 型注釈の必須性 | ✅ 不要（`.st` はオプション） |
| 高階関数の型解決 | ✅ `$`/`@` による明示的な Lambda↔Atom 変換 |
| モジュール境界の型解決 | ✅ `.st` ファイル（静的）または `__` 単位元フォールバック（動的） |
| 関数適用の安全性 | ✅ 完全性公理（`f __ = __`）による例外なし収束 |
| struct の `==`（構造比較） | ✅ Hom集合の一致。コンストラクタ名は参照しない（区別は `' !__` で opt-in） |
| 関数仮引数のフィールド要求 | ✅ `.st` に自動生成（検証の強制は別途方針） |
| enum バリアントの実行時識別 | ✅ 自動番号付け（C同様の異なる Int 定数）により、普通の Int 比較に帰着（6.2参照） |
| Lambda 返値型の静的決定 | ✅ `?` 右辺の演算子連鎖から一意に決定 |
| enum（直和型）の表現 | ✅ `match_case` の `|` チェーンから自然に導出される（専用構文不要）。ただし呼び出し元がどの物理表現で受け取るかの検証は行わない（C の union と同様、自己責任） |
| `|` 演算子の二重性 | ✅ 値レベル（短絡評価）と型レベル（直和型生成）の両立 |
| `$`/`@` の演算子意味の静的決定 | ✅ Pass 1 識別子テーブルにより Lambda/Address をコンパイル時に決定 |

> [!NOTE]
> **型システムの根拠**
>
> 全ての型は `Unit`（`__`）を根拠とします。
> Unit は双代数の単位元であり、全ての演算に対して一貫した単位元・吸収元として機能します。
> `Self-referential` な Sign の表現は常に `Unit` に帰着できるため、
> SignType（`.st`）による外延的な自己言及を通じて、型システムの無矛盾性が保証されます。
